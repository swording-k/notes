# 飞书项目管理 Agent · 讲解 PPT 大纲（Storyboard）

> 用途：给研发同事做需求讲解 + 让一骢哥验证场景理解是否准确
> 讲完时长：10–15 分钟
> 版本：框架版（本文件为大纲 / 目录结构，讲解口语与每页"为什么"叙事由杨锟本人撰写）
> 依赖：Demo 全链路验收（任务③）完成后，再补 P9/P10 真实截图与 P11 收益数字

---

## 讲述主线（一句话收束全篇）

**不是替代禅道，而是替代"需求从产生到进禅道之前"那一串靠微信私聊、人工通知、手工整理的低效动作**——让协调角色从"信息搬运工"变成"需求审核员"。

## 页面清单（建议 14 页）

### P1 · 封面
- 标题：飞书项目管理 Agent 讲解
- 副标题：从群聊到可追溯需求池
- 演讲人 / 日期 / 项目名占位

### P2 · 背景与痛点（As-Is）
- 现状流程图：需求在微信私聊 / 会议里定 → 人工通知仕兴姐 → 手填禅道 → 开发承接
- 三个痛点：上下文聊完即过、版本被覆盖、反复追问"当时怎么定的"
- 素材来源：业务流程拆解 §2.2（As-Is 全景）

### P3 · To-Be 工作流总览（一页图）
- 八阶段：项目启动 → 需求提出 → 讨论试错 → 决策确认 → 开发排期 → 开发跟踪 → 测试验收 → 上线
- 素材来源：业务流程拆解 §4.1 总览表

### P4 · 每阶段三要素（可拆 1–2 页）
- 每阶段说清：团队在做什么 / Agent 自动做什么 / 沉淀什么数据
- 素材来源：业务流程拆解 §4.1 三列

### P5 · Agent 架构图
- 链路：消息接入（事件订阅）→ 识别 → 关联 → 写入 → 建议 → 输出
- 运行载体：Aily 平台 Agent + lark-cli
- 素材来源：PRD §4 架构图 + §5.1 消息处理主流程

### P6 · 核心机制：一句话需求 → 试错 → 收敛
- 状态机：待澄清 → 进行中 → 已收敛 / 已搁置
- 版本链：v0 / v1 / v2 追加不覆盖
- 素材来源：PRD §6 业务承接机制

### P7 · 技术实现方式
- 栈：Aily 平台 Agent + lark-cli + 多维表格（需求池）+ 云文档（决策日志）
- 为什么不用"团队智能伙伴"：监听全群消息（非仅 @ 触发）是核心能力，零代码方案做不到
- 素材来源：PRD §4 架构选型说明 + §9.2

### P8 · 能力补强：资源冲突识别
- 主动识别撞车 / 依赖风险 / 排期矛盾，给一句 PM 解读 + 2–3 条澄清提示
- 素材来源：PRD §6.4

### P9 · Demo 演示：核心能力（Step 1–3）
- 新需求识别并建议合并、决策拍板自动建任务、开工反馈自动更新排期
- ⚠️ 待 demo 全链路验收后补真实截图（任务③）

### P10 · Demo 演示：进阶 / 高级（Step 4–6）
- 主动识别资源冲突、状态自动流转、@Agent 更新决策日志
- ⚠️ 同上，依赖验收

### P11 · 价值与成本收益
- 成本：一次性搭建 + 杨锟持续调优维护；日常不改变团队禅道 / DevOps 习惯
- 收益（估算，待校准）：仕兴姐 / 一骢哥花在"信息搬运 + 重复确认"的时间由约 2–3h/周降至 0.5h/周；开发追问背景时间下降
- ⚠️ 数字待结合验收与真实数据校准，避免拍脑袋

### P12 · 动作替代清单（正面回应一骢哥"替代什么"）
- 表格：现有动作 / 谁在做 / 价值高 or 低 / 保留 or 替代 / 怎么替代
- 示例行：微信私聊定需求（高，保留沟通形式，迁飞书自动沉淀）；口头通知仕兴姐填禅道（低，替代，Agent 自动生成禅道草稿）；手填禅道卡（中，保留但改为审核草稿后一键确认）；周报手动汇总（低，替代，Agent 自动推送）
- ⚠️ 待结合一骢哥反问补全定稿
