## 〇、方向纠偏：从「禅道前置」到「群聊原生替代禅道」

**此前的误判**：我们一直以为禅道是公司强制自有部署、人人必用的系统，因此把产品定位成「禅道前置的沟通沉淀层」，反复强调「不替代禅道」。

**一骢哥的真实意图**：他要的恰恰是**用群聊智能体替代禅道**。核心痛点是——在禅道里建一个项目、每新建一个需求都要填一堆表，很麻烦；如果能**在群里一句话就完成需求建立和项目管理**，体验会好得多。

**结论性定位**：
- 本产品不再是禅道的「前置动作」，而是**群聊原生的项目管理本身**。
- 若公司合规上仍要求项目落在禅道，则禅道只建一个**公共项目做合规壳**，中间完整的项目管理由我们的智能体完成。
- 因此，原来的「需求池」远远不够，**必须按成熟项目管理的完整框架重新设计**——包括你提到的**人员分配、工时分配**，以及排期、里程碑、进度量化等。

## 〇·五、对方案可行性的澄清（回应你的疑问）

写方案时我确实把数据模型铺得太重了（7 张表），你下面几个疑问正好点出要收口的地方：

**1. 「敏捷」是不是「敏捷开发」？我们算哪种？**
敏捷 / Scrum 和瀑布是项目管理的**方法论流派**，不是必选项。禅道、飞书项目这类工具支持敏捷，但我们要做的「群聊轻量 PM」初期根本不用 Sprint / 故事点 / 燃尽图那套——用「需求 → 任务 → 责任人 → 状态 → 周报」这条线就够跑通。所以**不用纠结团队是敏捷还是瀑布**，我们的轻量闭环两种都兼容。

**2. 多维表格是共享的，做不到「不同的人看不同的界面」？**
能做，但不是靠禅道那种权限系统，而是靠**「视图 + 筛选」**：在任务表上建一个「我的任务」视图，筛选条件设成「责任人 = 当前用户」，每个人点开就只看到自己的任务；再建「看板视图」（按状态）、「日历视图」（按截止日期）。这样不用 7 张表、也不用复杂权限，就实现了「各看各的」。

**3. 跑通业务闭环，最简需要什么？**
现有 Agent 已经能「群聊 → 需求 → 决策日志 → 周报」。**只差一个「责任人」字段**就能形成闭环：谁负责什么一目了然，周报自动汇总「谁在做什么」。工时、排期、进度量化是让管理更精细的**增强项**，不是跑通闭环的必需——骢哥说"想让 PM 工作轻松点"，Phase 1 做到「建任务 + 派给人 + 周报」就达标了。

**4. 7 张表太繁琐 → 已收紧为 3 表**
详见 §五，核心是一张任务主表 + 一张决策日志表 + 可选工时表，靠视图分流，不靠多表堆叠。

## 一、成熟项目管理是怎样的（方法论 + 工具双视角）

### 1.1 理论框架（PMBOK 第七版 + 敏捷）

**五大过程组**：启动 → 规划 → 执行 → 监控 → 收尾。

**十大知识领域**（与本项目强相关的重点）：
- **范围管理**：WBS 工作分解结构（需求 → 子任务拆解，100% 规则防遗漏）
- **进度管理**：排期、甘特图、关键路径法（CPM）、里程碑
- **成本管理**：预算、挣值分析（EVM）；轻量团队常简化为「工时」
- **资源管理**：人员分配、RACI 矩阵、资源直方图 / 人员负荷度
- **沟通管理 / 干系人管理**：状态报告、决策留痕
- **风险管理**：风险登记册、定性/定量分析、应对策略
- **质量管理 / 整合管理 / 采购管理**：随团队成熟度逐步启用

**敏捷 / Scrum**：Product Owner / Scrum Master / 团队三角色；Product Backlog → Sprint Backlog → 增量；计划会 / 每日站会 / 评审会 / 回顾会；故事点 + 速率（Velocity）+ 燃尽图。

**看板方法**：可视化工作流、限制在制品（WIP）。

### 1.2 主流工具功能模块对比

| 维度 | 禅道（开源/私有部署） | 飞书项目 | Jira | Linear |
|------|------------------|---------|------|--------|
| 需求管理 | 需求池：多级分类、优先级、状态流转、关联版本/迭代 | 需求 + IPD 评审流 | Epic / Story 层级 | Issue 层级 |
| 任务分解 | 子任务 + 父子需求；企业版支持甘特图 | **计划表：无限层 WBS + 甘特图 + 依赖 + 关键路径** | 子任务 / Sub-task | 子任务 |
| 人员分配 | 任务指派责任人、优先级、工期 | 基于「角色」的权限与流程驱动 | Assignee + 组件负责人 | Owner + 多人 |
| 工时 | 工时记录与统计 | 工时字段 | Log work（工时日志） | 估时（Estimate） |
| 排期 | 企业版甘特图；开源版弱 | 甘特图 + 依赖关系 + 自动排期 | 路线图 / 看板 | 周期（Cycle）/ 看板 |
| 进度跟踪 | 燃尽图（Scrum）、完成率 | 计划表进度 | 仪表盘 / 燃尽图 | 看板流速 |
| 报表 | 任务完成率、缺陷密度、**人员负荷度** | 自定义报表 | 丰富插件仪表盘 | 轻量 |
| 知识/文档 | 文档中心（PRD/纪要集中） | **聊天即任务，天然沉淀** | Confluence 联动 | 轻量 |
| 核心差异 | 性价比高、中文好，但**填表重** | **聊天即任务、OKR 打通** | 插件强但贵、中文弱 | 极简、研发体验好 |

### 1.3 对我们最关键的三个洞察

1. **「聊天即任务」是飞书项目的核心卖点**，正是一骢哥想要的。我们不采购飞书项目，而是用「群聊 + Aily Agent + 多维表格」**自建轻量版**——零迁移、零额外订阅。
2. **你最关心的「人员分配、工时分配」是成熟 PM 的标配**，对应 PMBOK 资源管理 + 工具的任务责任人 / 工时字段 / 人员负荷报表。这也正是禅道「填表最烦」的部分——我们用自然语言 + Agent 自动填，正好打中痛点。
3. **禅道的强项是「执行侧」（需求分配/工时/发布），弱项是「从对话自然沉淀」**。我们用群聊入口补上弱项，执行侧用多维表格字段对齐禅道，做到「体验轻、数据全」。

## 二、我们的新定位

**群聊原生项目管理（Chat-as-PM）**

> 以飞书群聊为唯一入口，Agent 把自然语言讨论实时转成结构化项目数据（需求 / 任务 / 分配 / 工时 / 排期 / 决策），多维表格为底层存储，实现「飞书项目级聊天即任务」的能力，但零迁移、零额外订阅。

**与禅道的关系**（回应一骢哥）：
- 理想态：禅道完全由本产品替代，团队只在群里协作。
- 合规兜底：若公司要求项目必须落在禅道，则禅道仅留**一个公共项目做合规壳**，实际 PM 全流程在我们这里完成；后续可选接禅道 MCP 做双向同步（非必须）。

## 四、须新增的核心功能（F10–F15，简版，详细 PRD 后续补）

**F10 任务分解与子任务**
- 做什么：需求可拆子任务，形成 WBS（多层父子关系）
- 触发：「把【X】拆成 3 个子任务：a/b/c」或 Agent 建议拆解
- 产出：任务表新增子行，父任务完成率 = 子任务加权

**F11 人员分配**
- 做什么：任务指派责任人 / 协同人
- 触发：@某人「你负责 X」或「把 X 派给张三」
- 产出：任务表「责任人 / 协同人」字段更新；成员表扩角色

**F12 工时管理**
- 做什么：工时填报与汇总
- 触发：「记录今天在 X 上花了 3h」或周报自动聚合
- 产出：新增工时表；周报增加「人员负荷」维度

**F13 排期与里程碑**
- 做什么：任务加开始 / 截止 / 里程碑节点
- 触发：「X 计划 8/20 上线」「标记 Y 为里程碑」
- 产出：任务表时间字段；多维表格日历 / 甘特视图呈现

**F14 进度量化**
- 做什么：用完成率 / 轻量燃尽图替代纯状态
- 触发：状态变更或子任务完成自动算
- 产出：项目表 / 周报展示完成率曲线

**F15 风险登记**
- 做什么：在资源冲突识别基础上扩成风险表
- 触发：检测到人员负载过高 / 排期冲突 / 依赖阻塞
- 产出：风险表 + 群内预警

## 五、新数据模型（极简版：3 表 + 多视图）

放弃原来的 7 表方案（过重，大家不知道看哪个）。改为 **1 张任务主表 + 1 张决策日志表 + 可选工时表**，靠「视图」解决"不同人看不同内容"，不靠多表堆叠。

### 5.1 任务表（唯一主表，承载 90% 数据）

| 字段 | 说明 | 来源 |
|------|------|------|
| 需求 / 任务描述 | 一句话需求或任务 | 群聊识别 |
| 类型 | 新需求 / 修改 / 决策 / 闲聊 | 分类 |
| **责任人** | 谁负责（@ 或「张三负责 X」） | Agent 解析（Phase 1 新增） |
| **协同人** | 协作人（可选） | Agent 解析（Phase 1 新增） |
| 状态 | 待澄清 / 进行中 / 已收敛（或 待开始 / 进行中 / 已完成） | 现有 |
| 优先级 | 高 / 中 / 低（可选） | 解析 |
| **开始日期 / 截止日期** | 排期 | 「X 计划 8/20 上线」解析（Phase 2） |
| **工时** | 预估 / 实际工时（小时） | 「记录今天在 X 花 3h」（Phase 2） |
| 关联决策 | 关联决策日志 | 自动 |
| 父任务 | 子任务归属 | F10 拆解（Phase 2 可选） |
| 来源 / 创建时间 | 群 / 私聊 / 妙记 | 现有 |

### 5.2 视图（解决"各看各的"，无需禅道式权限）

- **看板视图**：按状态分列
- **我的任务**：筛选 责任人 = 当前用户 → 每个人只看自己的
- **日历视图**：按截止日期
- **全部需求**：完整列表

### 5.3 决策日志表（独立，因是不同实体）

决策内容 / 关联任务 / 决策人 / 时间 / 背景

### 5.4 工时表（可选，Phase 2 再加）

若需要精细工时统计再加；初期可在任务表用「工时」字段粗略记。

> 周报 / 日报：由 Agent 从任务表动态聚合生成，**不单独存表**。
> 成员信息：无需独立成员表，责任人直接用飞书人员字段即可。

## 七、工程现实与边界（诚实评估）

**多维表格 + Agent 能覆盖**：需求→任务→分配→工时→状态→周报→决策→知识库→基础报表。技术上「一句话建需求/任务」已跑通（识别 + 写入），扩展为「一句话建任务 + 派给谁 + 预计工时」只需补 NLU 与确认机制。

**暂不强求（飞书项目 / IPD 专版才有）**：无限层 WBS + 关键路径自动计算、跨项目集（PPM）依赖、精细 RBAC 权限、正式评审流、挣值 EVM。我们做「够用的轻量 PM」，不追求飞书项目级复杂度——这正好符合一骢哥「轻量替代」的初衷。

**金融合规提醒**：工时填报若涉及考核，可能需强制 + 审计留痕；禅道公共项目壳的字段若用于合规报送，需与一骢哥确认口径。
