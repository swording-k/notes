## 一、整体架构

运行在飞书 Aily 平台上的「项目管理 Agent」以 **Continuous（常驻）任务**方式存活，通过三类触发消费宝剑群消息，把结构化结果写入飞书多维表格。

│   │ (Continuous) │                                          │
│   └──────┬───────┘                                          │
│          │                                                   │
│   ┌──────┴───────┐    ┌──────────────┐    ┌──────────────┐ │

│   │              │    │              │    │              │ │

**要点**
- Agent 是常驻进程，不是「被 @ 才活」的问答机器人。
- 三类触发共享同一个 Agent 与同一套多维表格，输出互相聚合（每日巡检汇总全天，生成每日速递 / 周报）。
- 宝剑群既是消息输入源，也是结果投递目标（报告发回群里）。

## 二、触发机制（3 层）

| 层级 | 触发条件 | 行为 | 输出 |
|------|---------|------|------|
| **即时响应层** | 被 @ 时 | 查状态 / 改状态 / 生成摘要 / 帮助 | 按需回复 |
| **智能感知层** | 检测到「确定了」「就这么定了」「排期」「约个会」「对齐一下」等收敛 / 安排信号 | 记录决策 / 会议安排 | **极简 1 句话** |
| **定时汇总层** | 工作日 16:35 / 周五 14:43 | 巡检全天消息，生成报告 | 每日速递 / 周报 |

> **静默原则**：其他时间完全静默，不会冒出来。这正是 PRD「不打扰」设计原则（§5 设计原则）的落地——Agent 默认旁听，只在识别到信号或被 @ 时才说话。

## 三、数据流

```
群消息 → 意图识别 → 分类（6类）
              │
    ┌─────────┼─────────┐
    ↓         ↓         ↓
  新需求    决策      会议安排
    │         │         │
    ↓         ↓         ↓
  任务表   决策日志   任务表
    │         │         │
    └─────────┴─────────┘
              ↓
         每日巡检聚合
              ↓
    ┌─────────┴─────────┐
    ↓                   ↓
  每日速递            每周周报
```

**6 类分类**：新需求 / 需求修改 / 澄清讨论 / 决策 / 闲聊 / 命令

- 新需求 → 任务表（建条目）
- 决策 → 决策日志表（极简 1 句话记录）
- 会议安排 → 任务表（排期类）
- 闲聊 → 静默忽略
- 命令 / 被 @ → 即时响应层处理

## 六、与 PRD v2.0 的映射

| PRD 功能 | 实际落地方式 | 状态 |
| --- | --- | --- |
| F1 多源采集 | 宝剑群消息 + 事件触发消费；私聊总结 / 会议妙记仍为规划态（当前仅群消息） | 部分（群聊 ✅，私聊/妙记 🔲） |
| F2 需求识别与沉淀 | 6 类分类 → 任务表写入 | ✅ |
| F3 版本链与状态机 | 任务表状态字段 + 版本链（待验证追加逻辑） | ✅ 基础 / 版本链待验 |
| F4 决策日志 | 决策日志表（收敛信号极简写入） | ✅ |
| F5 资源冲突与风险识别 | 暂未在 Auto 任务中体现 | 🔲 规划中 |
| F6 定时报告 | 每日巡检（工作日 16:35）/ 每周周报（周五 14:43）Auto 任务 | ✅ |
| F7 禅道衔接 | 暂为「需求背景草稿」，未接禅道 API | 🔲 草稿态 |
| F8 查询与交互 | 即时响应层（被 @ 查 / 改 / 摘要） | ✅ |
| F9 合规开关 | 收敛信号极简输出 + 静默设计（非触发不动作） | ✅ 设计层面 |

> 结论：当前实跑版本已覆盖 PRD 的「群聊监听 → 需求识别 → 决策留痕 → 定时播报 → 查询交互」主链路；**多源采集（私聊/妙记）、版本链追加、风险识别、禅道衔接**仍需按 PRD 规划态继续验收与补全。

## 七、验收样例（5 场景）+ 截图占位

> 每个场景在实际验证时需在飞书内跑一遍，并把**对应截图**贴入讲解 PPT 的占位框（见 PPT 验收场景页）。下方为「操作 → 预期」。

### 场景 1：连续对话合并
- **操作**：群里连续发 5 条同一需求的讨论
- **预期**：Agent 只生成 / 更新 **1 条**记录，不重复建 5 个条目
- 📷 截图占位：宝剑群对话 + 任务表仅 1 条记录

### 场景 2：版本链追加不覆盖原文
- **操作**：已有「协同平台字段扩展」记录，再发「再加个期望时间字段」
- **预期**：v0（原始一句话）保持不变，追加 v1，版本链显示 v0 → v1
- 📷 截图占位：任务表版本链字段

### 场景 3：@Agent 修改状态
- **操作**：@项目管理agent：「把【商机广场详情页改版】标记为已收敛」
- **预期**：Agent 回复确认，多维表格状态同步更新为「已收敛」
- 📷 截图占位：@指令 + 群回复 + 任务表状态变更

### 场景 4：收敛信号检测（极简 1 句话）
- **操作**：群里发：「这个需求就这么定了，先按 A 方案做」
- **预期**：Agent 回复：**「📌 已记录决策：将【XX 需求】按【A 方案】推进」**（仅 1 句话）
- 📷 截图占位：群内收敛信号消息 + Agent 极简回复

### 场景 5：任何写入都在群里给说明
- **操作**：@项目管理agent：「查一下协同平台字段扩展的状态」
- **预期**：Agent 回复查询结果，并附一句简短说明
- 📷 截图占位：查询指令 + 带说明的回复

## 八、范围与边界（对应 PRD §2.2 Non-goals）

- **不替代禅道**：禅道衔接当前仅为需求背景草稿，未接禅道 API 自动填报。
- **不碰代码 / 发布**：Agent 只管沟通沉淀，不涉及 DevOps / Code。
- **多源采集仍受限**：当前仅宝剑群消息，私聊总结 / 会议妙记采集为规划态，需实测飞书原生能力。
- **静默优先**：非触发（被 @ / 收敛信号 / 定时）不动作，避免打扰。
- **一次性核查任务**：进度核查为 cron 一次性任务，验证后可保留或清理。
