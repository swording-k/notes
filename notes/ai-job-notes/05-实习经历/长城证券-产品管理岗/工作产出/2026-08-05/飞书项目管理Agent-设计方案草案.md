## 3. 草案设计（核心）

### 3.1 Agent 整体架构

```
飞书群消息
    ↓
[消息接入层]  飞书 Bot + 群聊天记录接口 / 事件订阅
    ↓
[意图/内容识别]  LLM 判断：闲聊 / 需求 / 变更 / 决策 / 进度
    ↓
    ├─ 需求类  →  [需求池] 多维表格：记录需求 + 版本 + 状态
    ├─ 变更类  →  [需求版本更新] 关联到已有需求，追加版本
    ├─ 决策类  →  [决策日志] 飞书文档，按时间记录
    ├─ 进度类  →  [进度看板] 多维表格看板视图
    └─ 闲聊类  →  静默记录或忽略
    ↓
[PM 建议生成]  基于需求池 / 决策日志 / 进度，生成建议
    ↓
[响应输出]  Bot 在群里推送 或 更新飞书文档 / 表格
```

### 3.2 消息处理流程（核心流程）

| 阶段 | 输入 | 处理 | 输出 | 触发方式 |
|---|---|---|---|---|
| 1. 采集 | 飞书群消息 | 通过群聊天记录接口拉取 / 事件订阅接收 | 原始消息流 | 事件触发 / 定时拉取 |
| 2. 识别 | 原始消息 | LLM 分类 + 关键信息抽取 | 结构化条目（需求/变更/决策/进度/闲聊） | 自动 |
| 3. 关联 | 结构化条目 | 匹配已有需求池 | 更新到对应需求版本 | 自动 |
| 4. 建议生成 | 需求池 + 决策 + 进度 | 规则 + LLM | PM 建议（待办/风险/进度提醒） | 定时 or @触发 |
| 5. 输出 | PM 建议 | Bot 推送 / 文档更新 | 群内消息 + 飞书文档/表格更新 | 自动 or 手动 |

### 3.3 PM 方法论选型（我的初步选择）

聪哥说没硬性要求，符合基础知识即可。我选 **「轻量看板 + 需求演进日志」** 的组合：

| 组件 | 内容 | 为什么选 |
|---|---|---|
| 需求池 | 多维表格，字段：需求 ID / 原始一句话 / 当前版本 / 状态 / 关联消息 | 承接「一句话 → 试错修改」，能看演进 |
| 看板 | 需求池的看板视图（待澄清 / 进行中 / 已收敛 / 已搁置） | 研发团队熟悉，轻量 |
| 决策日志 | 飞书文档，按时间记关键决策 | 群里决策容易散，需要单独沉淀 |
| 周报/提醒 | Bot 定时生成 | 减少手工整理 |

**请聪哥拍板：这个组合是否过重？要不要再砍？**

### 3.5 「一句话需求 → 试错修改」承接机制（关键设计）

这是聪哥强调的业务形态，我单独设计承接方式：

| 业务特征 | Agent 承接机制 |
|---|---|
| 一句话需求 | 识别模糊需求雏形 → 入需求池，状态「待澄清」，原始一句话完整保留 |
| 试错修改 | 每次群里讨论该需求 → 识别为变更 → 在需求池追加版本（v1/v2/v3…），不覆盖原文 |
| 收敛 | 需求状态从「待澄清」→「进行中」→「已收敛」，状态变更需群内显式确认 |
| 演进呈现 | 飞书文档自动生成「需求演进卡」，展示一句话 + 各版本 + 当前定义的链路 |

> 这部分是我对聪哥「持续迭代」要求的具体化，**请重点反馈这个设计是否抓到了点子**。

### 3.6 研发团队场景示例（具体化）

假设研发群里有这样一段对话：

```
A：那个登录接口加个验证码吧
B：验证码用图形还是短信？
A：先图形，后面再说
（一天后）
A：图形被刷得太厉害，改短信
B：短信要花钱，要不要加个频控
A：加，每分钟一次
```

Agent 应该做的：

| 时刻 | Agent 动作 | 需求池状态 |
|---|---|---|
| A 首句 | 入池：需求#01「登录加验证码」v1「图形」，状态待澄清 | #01 v1 |
| B 追问 | 识别为澄清讨论，暂不改动 | #01 v1 |
| A「先图形」 | 更新 v1=图形，状态=进行中 | #01 v1 |
| A「改短信」 | 追加 v2=短信，状态=进行中 | #01 v1, v2 |
| B「加频控」 | 识别为衍生需求#02「验证码频控」v1=每分钟一次 | #01 v2, #02 v1 |
| 周末 | Bot 推送：本周需求演进卡（#01 图形→短信，#02 新增频控） | - |

### 3.7 可行性说明与当前不确定点

**已确认可行的部分：**
- 飞书 Bot 进群、收消息、@回复：官方能力，有文档。
- 群聊天记录接口：飞书开放平台提供，可获取群历史消息。
- 多维表格 / 云文档 API：均有开放接口，可读写。
- LLM 做分类 + 关键信息抽取：能力成熟，可通过提示词实现。

**需要踩点验证的部分：**
- 事件订阅的实时性和稳定性（是否存在延迟、漏消息）。
- LLM 对「需求 / 变更 / 决策 / 进度 / 闲聊」五类识别的准确率。
- 需求关联匹配：当群里讨论一个已有需求时，Agent 能不能正确匹配到需求池里的对应条目。
- 状态变更的群内确认交互：Bot 问「是否把 #01 标记为进行中？」，成员回复「确认」还是点按钮，需要看飞书 Bot 支持的交互形式。

**demo 阶段可简化的地方：**
- 不追求 100% 识别准确率，先跑通主路径。
- 多需求关联先用「关键词/需求标题相似度 + LLM」兜底，复杂语义关联留到后续优化。
- 状态变更确认先用「@Bot 回复关键词」这种简单交互，不强制做卡片按钮。
