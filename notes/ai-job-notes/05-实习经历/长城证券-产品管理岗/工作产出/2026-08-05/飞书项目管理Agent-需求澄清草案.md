## 2. 任务定位

### 2.1 demo 真正产物

**一个能跑在飞书群里、辅助研发团队管理项目的智能体（Agent）。**

它不需要替代项目经理，只需要在群里做三件事：
1. 记录聊天中的关键信息；
2. 提取/跟踪项目需求及其演进；
3. 给出 PM 层面的建议（待办、风险、进度提醒等）。

### 2.2 「持续迭代」是被体验的设计过程

业务部门很多时候是一句话需求，然后在群里不断试错、修改、收敛。这个 Agent 要能承接这种动态演进，而不是只记录最终结论。

实习生在设计 Agent 的过程中，也要亲身体验这种 **「一句话需求 → 试错 → 修改 → 收敛」** 的循环，并据此迭代 Agent 设计。

> 这不是一句口号，而是 demo 的核心设计哲学：**Agent 必须能承接业务的动态演进。**

### 2.3 不在范围内的事（明确排除）

| 排除项 | 说明 |
|---|---|
| 改「手拉手协同助手」现有代码 | 未要求在现有代码上修改，那是另一个 agent |
| 从 0 全新硬写 | 不强制；可参考已有设计思路 |
| 对齐团队现有 PM 方式 | 没有要求，按基础知识自己设计即可 |
| 给某个具体业务群上生产 | demo 阶段，先自测可用 |
| 把企微作为落地环境 | 企微做不了，飞书做 |

## 3. 场景设定

### 3.1 核心场景假设

**项目成员全在一个飞书群里沟通和给反馈。** Agent 在群里旁听、识别、记录、整理。

### 3.2 业务形态背景（Agent 必须支持的形态）

| 业务特征 | 对 Agent 设计的含义 |
|---|---|
| 一句话需求 | Agent 要能从零散、模糊的群聊中捕捉需求雏形 |
| 不断试错修改 | Agent 要能跟踪需求的演进版本，不是只记最新一条 |
| 收敛过程 | Agent 要能呈现需求从模糊到清晰的演进链路 |

> 这是聪哥明确强调的业务事实。Agent 设计的成败，很大程度取决于能否承接这种形态。

## 4. 技术选型与实现方式

### 4.1 平台选型理由

| 维度 | 飞书 | 企微 |
|---|---|---|
| 群聊天记录获取接口 | 有 | 查到没有 |
| 能否做此 demo | 能 | 不能 |

→ **demo 落飞书**。公司日常用企微，但企微缺关键技术能力，本任务不在企微上做。

### 4.2 实现方式

| 项 | 要求 |
|---|---|
| 主体 | 实习生自己设计 Agent |
| 资源 | 综合使用飞书 bot、群聊天记录接口、多维表格、云文档、事件订阅等原生能力 |
| 现有代码 | 不要求改「手拉手协同助手」代码；可参考其设计思路 |
| 全新程度 | 不强制从 0 写，也不强制复用；按合理方式自行决定 |

### 4.3 场景优先级

**先考虑研发团队场景。**

### 4.4 PM 方法论

| 项 | 要求 |
|---|---|
| 项目管理怎么管 | 没有具体要求 |
| 标准 | 符合基础知识即可 |
| 是否需对齐团队现状 | 否 |

## 5. 交付与用途

### 5.1 交付路径

```
实习生自测可用 → 给团队使用 → 实习生借此体验产品工作流程
```

### 5.2 demo 用途

1. **团队侧**：拿到一个能辅助 PM 的飞书 Agent。
2. **实习生侧**：通过设计与使用过程，体验产品工作流程——特别是 **「一句话需求 → 试错迭代」** 的持续演进逻辑。

## 6. 验收标准（建议）

| 维度 | 标准 |
|---|---|
| 能跑通 | Agent 在飞书群中能接收消息、调用工具、给出响应 |
| 能记聊天 | 通过群聊天记录接口拿到群消息并处理 |
| 能提需求 | 能从群聊中识别出项目需求（含一句话需求） |
| 能跟演进 | 能跟踪同一需求的多次修改/试错，呈现演进链路 |
| 能给建议 | 给出 PM 层面建议（待办/风险/进度等，形式自定） |
| 自测通过 | 实习生在研发团队场景下自测可用 |
| 业务形态支持 | 至少 demo 出「一句话需求 → 试错修改」的承接能力 |

> 验收标准为建议项，聪哥可调整。

## 7. 待实习生自行决策的开放问题

以下不在聪哥要求范围内，由实习生自行设计：

1. PM 方法论具体怎么设计（符合基础知识即可）。
2. Agent 架构怎么搭（LLM / 工具 / 状态机 / 提示词）。
3. 飞书哪些能力组合使用（bot + 文档 + 多维表格？）。
4. 如何在 Agent 中体现「一句话需求 → 试错修改」的承接。
5. 项目管理建议的具体形式（推送待办？生成周报？风险预警？）。

## 附：本需求澄清的关键判断

1. **产物是 Agent，不是工具脚本**——要给团队用，不是一次性 demo。
2. **业务形态是设计输入，不是装饰**——Agent 必须承接持续迭代。
3. **实现方式留有弹性**——不强制代码路径，但排除「改手拉手代码」。
4. **PM 方法论放手**——给实习生设计空间，只设基础知识底线。
