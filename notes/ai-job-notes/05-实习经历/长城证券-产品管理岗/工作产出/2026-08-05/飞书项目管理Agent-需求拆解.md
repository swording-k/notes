# 飞书项目管理 Agent · 需求拆解

## 1. 文档信息

| 项    | 内容                             |
| ---- | ------------------------------ |
| 任务名称 | 飞书项目管理 Agent 探索 Demo           |
| 执行人  | 实习生                            |
| 当前阶段 | 需求确认 → 设计定稿                    |
| 目标平台 | 飞书（企微暂无法提供群聊上下文接口，不做落地环境）      |
| 验证场景 | 手拉手协同平台 / 长城长 / 商机广场 迭代项目群（10 人左右） |
| 交付形态 | 可自测的群聊 Agent Demo + 需求拆解 + PRD |

## 2. 任务一句话

在飞书研发项目群里，部署一个能**旁听群聊、识别需求、沉淀看板、给出管理建议**的 AI Agent，让「一句话需求 → 群里讨论试错 → 逐步收敛」的全过程被自动记录和追踪。

## 3. 目标用户与场景

### 3.1 目标用户

- **主要用户**：项目负责人（项目经理）——负责把控迭代进度、需求澄清和状态收敛，不是产品经理。
- **次要用户**：群内迭代成员（产品、前端、后端、测试等，自然聊天即可，无需改变习惯）
- **观看用户**：导师 / 一聪哥（评估 demo 是否体现产品工作流程）

### 3.2 核心场景

项目成员全部在一个飞书群里沟通和反馈。Agent 不做群主，也不打断正常聊天，只在以下时机介入：

1. 群里冒出一句看起来像需求的话，Agent 默默记进需求池；
2. 成员继续讨论、修改方案，Agent 把讨论识别为「同一需求的版本演进」；
3. 讨论出现决策或卡点，Agent 在合适时机给出提醒、建议或状态更新；
4. 每天 / 每周 Agent 自动输出一份极简项目看板摘要。

## 4. 用户旅程与核心用例

### 4.1 旅程一：需求从混沌到澄清

| 步骤 | 用户行为                      | Agent 行为               |
| -- | ------------------------- | ---------------------- |
| 1  | A 在群里说：「商机广场详情页把『审核人员』改成『审核员』吧」 | 识别为潜在需求，写入需求池，状态=待澄清   |
| 2  | B 问：是只改展示文案，还是后端字段也改？        | 识别为澄清讨论，挂到该需求下         |
| 3  | A 说：文案先改，字段名不动，不然接口要联动     | 更新需求版本 v1，状态=进行中       |
| 4  | 第二天 A 又说：运营说字段名也要统一，不然对不上口径 | 追加版本 v2，保留 v1 历史       |
| 5  | B 问：那已发布状态的商机要不要批量刷新？A：要   | 识别为新增需求「批量刷新已发布商机状态」，原需求关联衍生 |
| 6  | 周末                        | Agent 自动推送：本周需求演进卡     |

### 4.2 旅程二：负责人快速掌握项目状态

| 步骤 | 用户行为                     | Agent 行为           |
| -- | ------------------------ | ------------------ |
| 1  | 负责人 @Agent：「这周进度」        | 从多维表格读取需求池状态，生成回复  |
| 2  | 负责人 @Agent：「#01 怎么样了」    | 返回该需求的完整演进链 + 当前版本 |
| 3  | 负责人 @Agent：「把 #01 标为已收敛」 | 更新表格状态，并在群里确认      |

## 5. 功能需求

### 5.1 Must Have（不做就不是这个 demo）

| #  | 功能     | 说明                             |
| -- | ------ | ------------------------------ |
| M1 | 群聊消息监听 | Agent 能收到群聊消息（含 @ 和非 @），作为输入源  |
| M2 | 需求识别   | 从闲聊中识别出「看起来像需求」的句子             |
| M3 | 需求池写入  | 把识别出的需求写入飞书多维表格，含原始一句话、状态、创建时间 |
| M4 | 版本演进   | 同一需求的后续讨论能追加版本，不覆盖原文           |
| M5 | 状态流转   | 支持 待澄清 → 进行中 → 已收敛 / 已搁置       |
| M6 | 群聊响应   | 被 @ 时能回答需求状态、生成摘要              |

### 5.2 Should Have（做了体验更好）

| #  | 功能     | 说明                     |
| -- | ------ | ---------------------- |
| S1 | 决策日志   | 把关键决策自动写入飞书云文档         |
| S2 | 衍生需求识别 | 讨论中冒出的新需求能单独成条，并与原需求关联 |
| S3 | 定时周报   | 每天/每周自动推送需求看板摘要        |
| S4 | 闲聊过滤   | 区分「需求/决策/闲聊」，闲聊不写入需求池  |

## 6. 验收标准

Demo 通过自测，需同时满足：

1. **输入**：群里连续 5 条以上关于同一需求的对话，Agent 能识别并只生成 1 条需求主记录；
2. **演进**：对话中出现修改时，Agent 在原记录下追加新版本，不丢失原始一句话；
3. **状态**：负责人 @Agent 可以把需求状态改为 已收敛，表格和群回复同步更新；
4. **独立**：关闭模拟 Bot 后，真人用户在群里说话，Agent 仍能完成识别和记录；
5. **可解释**：Agent 任何写入/更新操作都能在群里给出一句简短说明。

## 7. 范围边界

- 不强制对齐团队现有 PM 方式，用轻量看板即可；
- 不在真实业务群生产部署，demo 阶段只在测试群自测；
- 企微仅作背景说明，本次 demo 落地平台为飞书。

## 8. 成功指标

| 指标      | 目标                  | 如何验证 |
| ------- | ------------------- | ---- |
| 需求识别准确率 | 模拟 10 条对话，正确识别 ≥7 条 | 人工核对 |
| 版本追加准确率 | 同一需求 3 次修改后，版本链完整   | 人工核对 |
| 群响应可用性  | 被 @ 后 5 秒内返回有效信息    | 实测   |
| 可演示性    | 能在 10 分钟内完整跑完一个研发场景 | 现场演示 |

## 9. 自测方式（无真实研发团队时）

> 原置于「用户旅程」章节（§4.3）。因它描述的是测试方法而非用户旅程，按文档清理要求移出，单独成节。
