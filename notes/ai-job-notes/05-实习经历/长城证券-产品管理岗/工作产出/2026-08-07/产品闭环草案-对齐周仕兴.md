# 产品闭环理解草案（对齐用 · 待与周仕兴确认）

> 说明：本草案为与周仕兴（禅道需求发起人）对齐前的内部梳理。文字待本人定稿后再使用，勿直接转发。

## 一、当前需求管理现状（基于调研，待她确认）

- 一聪哥分配任务 → **周仕兴在禅道建卡 / 发起需求** → 作裕哥等成员在禅道承接、开发 → 同步 DevOps 提测上线。
- 讨论发生在私聊 / 开会 / 群，但**群几乎不聊、讨论过程不留存**；禅道只记结构化任务（做什么 / 谁做 / 何时完），不记"为什么这么定、怎么讨论的、谁拍的板"。
- 数据锚点：作裕哥的需求在禅道上发起人为周仕兴 → 她是禅道入口的关键人。

## 二、我们设计的闭环（多源沟通 → 统一沉淀 → 衔接禅道）

1. **线上交流**：飞书群聊 / 私聊，聊完把总结或结果发回群 → 被项目管理 Agent 记录进多维表格（需求池 + 决策日志）。
2. **线下交流**：用飞书妙记录音 → 自动生成结构化纪要 → 发到群 → 同样进多维表格。
3. **衔接禅道**：周仕兴（或 agent 辅助 / 手动）把多维表格里的需求与禅道连接——
   - 自动：禅道有 REST API，agent 可直接建 / 改需求卡（推荐路径，免去手抄）；
   - 手动：未接 API 前，由人对照抄录（仅作临时兜底）。
- **定位**：我们是**禅道的前置 / 沟通上下文层**，不替代禅道（任务 / 代码 / 提测 / 上线仍归禅道 + DevOps）。

## 三、带去问周仕兴的关键问题

1. **字段**：你在禅道建需求卡实际填哪些字段？哪些是我们 agent 抓取的"讨论上下文"能帮你省力的？
2. **连接方式**：多维表格 → 禅道，你倾向 agent 自动推（禅道有 API，需账号 + 模块权限 + token，且要内网可达），还是你审核后手动建？
3. **职责边界**：作为发起人，你是代开发建卡，还是审核开发提的卡？agent 该介入哪一步、是否保留你这个"人"把关？
4. **合规**：agent 碰禅道数据（即使只读、或只回写"决策背景"备注）你们接受吗？API 凭证应放在哪（建议公司内网受控环境，而非个人机器）？

## 四、Non-goals（暂不做的，避免谈歪）

- 不替代禅道任务管理 / 不碰代码 / 不碰提测上线；
- 不读微信私聊（无官方接口，且合规上不该读）；
- 敏感会议可关闭 AI 纪要（金融合规保留开关）。
