# 业务流程拆解：群聊 AI 项目管理助手如何融入现有研发协作流

> 说明：本文业务流程拆解，重点思考项目管理 Agent 在整个业务中的位置，也就是调研该需求价值。内容基于 2026-08-07 与陈作裕、周仕兴等团队人员访谈，以及飞书/禅道/DevOps 工具查证。

---

## 一、为什么要做这次拆解（Why）

此前 PRD 与产品设想的底层假设是"大家在群里聊需求、AI 在群里管需求"。但经过对真实业务的访谈，这个假设需要修正：

- **聊天**：每个项目团队的项目微信群里，日常发消息，例如每次发版都会在群里通知；
- **但"需求怎么提、怎么定、怎么进系统"并不发生在群里**：一骢哥通常是与每位成员私聊来分配和确认需求，而私聊主要发生在**微信**上——因为团队里有大量外包人员，日常工作沟通都在微信；  
  微信群里的工作聊天（含需求交代、发版通知）和以后飞书群里聊的内容，本质都是同一类东西；差别在于**微信缺少沉淀机制**——需求与决策背景聊完即过，事后难以追溯，而飞书天然具备群消息、妙记、多维表格、知识库等可沉淀能力；
- 禅道对团队来说本质是**记工时 / 记任务的执行主数据系统**，不负责沉淀讨论上下文。

所以本产品的真实定位在于：**把团队的工作沟通承载到飞书，借助飞书的群消息、妙记（会议/线下录音转写）、多维表格、知识库等原生能力，让原本在微信里聊完即过的需求与决策背景自动被记录下来**——由智能体管理和沉淀为需求池、决策日志，以及由个人或群组留存的知识库。大家的禅道 / DevOps 习惯不改变，只是多了一层"聊过的东西能留得住"的载体。

## 二、现有业务流程全景（As-Is）

### 2.1 角色

| 角色        | 真实人物     | 在流程里的职责                                      |
| --------- | -------- | -------------------------------------------- |
| 决策者 / 分配者 | 一骢哥（杨一骢） | 与当事人聊定需求，通知周仕兴建卡；手拉手类或需求先与业务部门对接，再在实施时叫上开发   |
| 禅道录入 / 协调 | 周仕兴（仕兴姐） | 兼把需求填进禅道；是禅道需求的发起人；                      |
| 开发执行      | 陈作裕等成员   | 在禅道承接任务/需求，本地 IDE 开发，各自选择发布方式（devops/code……） |

### 2.2 流程（现状）

```
[需求产生] 微信一句话 / 会议 / 口头  ──(无留存)──┐
        │                                        │
        ▼                                        │
[一骢哥与当事人对聊定]  (私聊/开会, 无留存) ──────┤
        │                                        │
        ▼                                        │
[通知周仕兴]  ───────────────────────────────────┤
        │                                        │
        ▼                                        ▼
[周仕兴填禅道]  ──► [成员禅道承接/开发] ──► [各自发布]
                                     作裕哥: DevOps 交代码
                                     周仕兴: Code 直接发版
                                      (发布方式不统一, 非都走 DevOps)
        │
        ▼
[禅道记工时 / 任务状态]
```

**关键观察**

- 两个环节（需求产生、对聊定）**无留存**——这是本产品要补的洞。
- **发布环节不都走 DevOps**
- 禅道是**执行主数据 + 工时系统**，不是需求讨论的载体。

## 三、我们的产品在哪里介入（To-Be）

### 3.1 介入原则

> **做"加法"不做"迁移"**：在现有流旁边补一层捕获与上下文沉淀，**不要求任何人改变禅道/DevOps 习惯**，也不要求把存量工作迁到飞书。

### 3.2 多源采集 → 统一沉淀

无论沟通发生在哪，最终都汇到同一套"需求池 + 决策日志 + 知识库"，由群内 PM Agent 统一抽取、去重、合并——这就是"多源采集、统一沉淀"。

| 沟通来源      | 在飞书里的采集方式                    | 进入项目群的方式            | 统一沉淀去向                |
| --------- | ---------------------------- | ------------------- | --------------------- |
| 飞书群聊      | PM Agent 原生读取群消息（事件订阅）       | 天然在群内               | 需求池（多维表格）/ 决策日志 / 知识库 |
| 飞书私聊      | 个人智能伙伴总结对话                   | 人转发 或 配置助手自动推送到项目群  | 同上                    |
| 会议 / 线下对话 | 妙记（飞书内置语音转录总结功能）录制转写，生成结构化纪要 | 飞书自动推会议群 / 手动分享到项目群 | 同上                    |

### 3.3 各角色在 To-Be 里的动作（Agent 每环节做什么）

| 环节        | 谁做           | Agent / 团队成员做什么              | 产出数据            |
| --------- | ------------ | ---------------------------- | --------------- |
| 需求产生 / 讨论 | 一骢哥，产品经理，当事人 | 线下交流：可用“妙记”录音总结； 线上私聊由个人助手总结 | 原始沟通记录          |
| 沟通聚合      | PM Agent（群内） | 消费群消息 + 妙记纪要，抽取需求/决策，去重合并    | 多维表格：需求池条目、决策日志 |
| 需求确认      | 所有人          | 都可以审核和查看多维表格里的需求，把关          | 已确认的需求条目        |
| 衔接禅道      | 周仕兴          | 把需求和任务填到禅道上                  | 禅道需求卡           |
| 开发 / 发布   | 成员           | 不变，仍禅道 + DevOps/Code         | 禅道工时 / 任务状态     |
| 定时同步      | PM Agent     | 每日/每周推送工作播报、需求提醒             | 群内播报            |

### 3.4 用户故事（核心角色）

- **作为一骢哥**，我希望讨论结论自动沉淀成可追溯记录，以便日后能查"当时为什么这么定、谁拍的板"。
- **作为周仕兴**，我希望 Agent 把散落的讨论先整理成需求池，以便我审核后一键建卡。
- **作为开发人员（作裕哥等）**，我希望需求背景有记录可追溯，以便理解"为什么这么做"而不用反复追问。
- **作为新人 / 接手者**，我希望有一个需求池能看项目全貌与决策脉络，以便快速上手。

## 四、有了本产品之后的完整项目管理工作流（To-Be 全周期演练）

本产品接入后，一个项目从启动到上线的全过程如下。每个阶段都标注三件事：**团队在做什么 / Agent 自动做什么 / 沉淀下什么数据**——这正是"业务流程拆解"要回答的核心。

### 4.1 全周期总览

| 阶段   | 团队在做什么                       | Agent 自动做什么              | 沉淀的数据                |
| ---- | ---------------------------- | ------------------------ | -------------------- |
| 项目启动 | 建飞书项目群、拉成员、明确目标              | 进群、初始化需求池与决策日志、搭好知识库框架   | 项目空间、空需求池            |
| 需求提出 | 在群 / 私聊 / 会议中提出想法（飞书原生承载）    | 读取群消息与妙记纪要，自动抽取"疑似需求"    | 需求池草稿条目              |
| 讨论试错 | 多轮讨论、方案比对（含线下妙记）             | 持续捕获讨论、合并同一需求的多个版本、标注未决点 | 需求池（含版本链）、决策日志（讨论过程） |
| 决策确认 | 一骢哥拍板，明确范围与负责人               | 把拍板结论写入决策日志、标记需求为"已确认"   | 已确认需求、决策记录           |
| 开发排期 | 周仕兴在禅道建卡、分配                  | 把需求背景同步到禅道卡备注（或先给草稿供确认）  | 禅道需求卡（衔接）            |
| 开发跟踪 | 成员开发、更新禅道状态                  | 每日 / 周推送工作播报、需求进展提醒、风险预警 | 群内播报、周报              |
| 测试验收 | 提测、验收                        | 汇总验收结论到决策日志              | 决策日志（验收）             |
| 上线   | 发布（DevOps / Code 各自方式）、群内发通知 | 捕获上线通知、沉淀复盘、更新需求状态为"已上线" | 需求池状态、知识库复盘          |

### 4.2 一个完整例子（以"协同进度看板"需求为例）

1. **项目启动**：一骢哥为"手拉手协同系统"建飞书项目群，拉入周仕兴、作裕哥等成员，PM Agent 进群。
2. **需求提出**：一骢哥在群里提到"业务部门希望实时看到协同进度，我们加个看板"；同时线下和作裕哥聊了技术可行性。Agent 抓到群消息与妙记纪要，在需求池生成草稿条目"协同进度看板"。
3. **讨论试错**：群里多轮讨论（看板展示哪些字段、是否实时）。作裕哥私聊一骢哥，指出"实时拉取会碰数据权限"。Agent 持续合并同一需求的多个讨论版本，并在需求池标注未决点"数据权限范围待定"。
4. **决策确认**：一骢哥拍板"先做部门级看板，实时性用定时刷新"。Agent 把拍板结论与理由写入决策日志，需求池条目标记为"已确认"。
5. **开发排期**：周仕兴在禅道建卡并分配给作裕哥。Agent 把需求背景与决策记录同步到禅道卡备注（未接 API 前则先给周仕兴一份草稿供她确认后建卡）。
6. **开发跟踪**：作裕哥开发并同步更新禅道状态。Agent 每周推送周报，并提醒"看板需求进行中，数据权限方案尚未关闭"。
7. **测试验收**：作裕哥提测，周仕兴组织验收。Agent 把验收结论汇总进决策日志。
8. **上线**：作裕哥发版，并在群内发上线通知。Agent 捕获通知，把需求状态更新为"已上线"，把本次从讨论到上线的脉络沉淀进知识库，供后续接手者查阅。

## 五、价值与提效论证（回答"能否提效 / 是否伪需求"）

团队成员的替换成本不高，因为 Agent 的调整优化和工作流的设计，由杨锟来做。

替换价值在于大家有更清晰的需求观看面板和知识沉淀记录。

**诚实前提**：填禅道本身已经很快（点几下）。

真实价值在禅道之前的"空白段"：

- **对周仕兴（关键干系人）**：不增加步骤。她的顾虑"多一步更繁琐"，并不存在，因为飞书中的这些文档和需求池不需要让仕兴姐管理。
- **对开发**：有了更高效的沟通和记录方式。
- **对一骢哥**：决策自动留痕，不用靠人肉记忆。
- **对组织**：需求背景可追溯，知识不随人走；新项目有统一需求池。

## 六、Non-goals（防止范围蔓延）

- 不替代禅道任务 / 工时管理，不替代版本提交平台；
- 不碰代码、提测、发布（DevOps / Code）；
- 不假设禅道 MCP 默认可用（扩展需求）；
- 敏感会议可关闭 AI 纪要（合规开关）；
- 不做"全量监听所有群消息"的无差别采集（仅项目相关群 + 经同意的会议/线下）。

## 七、待确认 / 风险

| 项        | 内容                                                          | 影响                                   |
| -------- | ----------------------------------------------------------- | ------------------------------------ |
| 禅道 MCP授权 | 禅道由别的团队管理，我认为是可以通过 MCP 实行自动化填报的，但是如果仕兴姐认为没必要的话，她以后继续手填也没关系。 | 和我们的产品并没有关系，只是向仕兴姐提出了可以提升填报效率的一个可能性。 |
| 内部飞书化假设  | 价值最大化依赖工作沟通迁飞书；外部干系人仍微信                                     | 影响采集覆盖率                              |
| 合规边界     | 沟通数据（含会议录音）需知情同意 + 敏感可关                                     | 金融场景过审前置条件                           |
