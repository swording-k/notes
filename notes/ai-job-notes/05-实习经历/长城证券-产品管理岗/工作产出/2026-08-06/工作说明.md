## 一、工作过程记录

### 1.1 重新规划：以产品经理视角重写

纠正方向后，从产品经理视角重新梳理，产出两份核心文档：

- **《需求拆解》**：明确任务一句话、目标用户与场景、用户旅程、功能需求、验收标准、范围边界、成功指标。
- **《PRD》**：明确产品定义、设计原则、推荐架构（飞书 aily「团队智能伙伴」方案）、消息处理流程、业务承接机制（一句话需求 → 试错 → 收敛的版本链）、数据模型、飞书能力映射、分阶段实施计划、关键决策点与风险。

场景贴近真实业务：以长城证券内部数字化平台（长城长 / 手拉手协同平台 / 商机广场）的迭代项目为模拟背景，而非泛泛的"登录加验证码"之类的外部案例。

### 1.2 手动实现与测试

- 在飞书中实际搭建模拟环境：创建「手拉手项目团队」群，拉入多个角色智能体（杨一骢、徐亚琴、前端、后端、测试、产品实习生等）模拟团队协作。
- 配置「项目管理 Agent」，并在群内通过真实对话驱动测试，验证核心功能。
- **当前 demo 已初步跑通 PRD 中的核心功能：自动管理需求**——即自动维护多维表格「需求池」与云文档「决策日志」。

## 二、技术实现与 PRD 的出入

在正式操作过程中，我发现 PRD 中的部分假设与计划，和真实可落地的环境并不完全一致。因此技术实现并未完全照搬 PRD 末尾推荐的「团队智能伙伴方案」，而是采用了更贴合实际条件的实现方式。

> 说明：以下记录 Demo 的真实技术架构。分为「已验证事实」和「基于文档推断」两部分——已验证部分来自实际测试与工具调用，推断部分会明确标注，不做夸大。

### 2.1 PRD 原推荐方案

- **方案**：飞书 aily「团队智能伙伴」作为 PM Agent 主载体——零代码、可进群、原生读群上下文、绑定多维表格 / 云文档 / 消息 / 任务。
- **理由**：上线快、权限继承飞书组织架构、无需自建后端。

### 2.2 实际落地方案（已验证）

**运行载体**：Agent （智能伙伴）运行在 **Aily 平台**上（系统明确声明的运行环境），并非飞书 aily 的「团队智能伙伴」零代码产品。

**群聊监听方式**：Agent 能够监听群里**所有消息**，不只是在被 @ 时响应——这一点已在测试中验证（群里每条消息都能被处理）。

- 触发机制（推断）：基于 Aily 平台文档，推测是通过\*\*事件订阅（Event Subscription）\*\*实现——飞书在群里有新消息时主动推送事件到 Agent，Agent 被唤醒后执行分析。具体配置指令未直接查看，推测为 `aily-cli auto --trigger-type event`。

**操作飞书资源的方式**：Agent 通过 **lark-cli（飞书开放平台 CLI）** 直接调用飞书 OpenAPI 来读写多维表格和云文档。已验证的调用：

- `lark-cli base +record-create` — 在多维表格新建任务（已验证，测试中成功写入）
- `lark-cli base +record-update` — 更新任务状态（已验证，状态流转成功）
- `lark-cli docs +update` — 更新决策日志文档（已验证，手动写入成功）
- `lark-cli im +messages-send` — 发送群消息（已验证，Agent 成功回复）

**本地持久化**：Agent 能读写本地文件系统（路径 `~/.aily/workspace/`），通过 file 工具实际执行过，非推断。已验证文件：

- `baojian-project/status.json` — 记录项目配置（表格 token、群 ID 等）
- `baojian-project/decisions.json` — 决策记录缓存
- `memory/*.md` — 每日会话日志

这些文件的作用是**跨会话保持状态**——每次事件触发都是新的会话执行，Agent 通过读取本地文件恢复上下文。

**LLM 推理层**：Agent 基于大语言模型做消息分类和实体提取。系统提示词定义了角色、消息分类规则（新需求 / 需求修改 / 决策 / 状态变更 / 命令 / 闲聊）、输出格式规范。模型不是"看到 XX 就做 YY"的写死规则，而是根据上下文推理后**自主决定**调用哪个工具、传什么参数。

### 2.3 与「团队智能伙伴」的区别（基于观察）

| 维度   | 团队智能伙伴（你在 aily 界面创建的） | 本 Agent（Aily 平台）              |
| ---- | --------------------- | ----------------------------- |
| 触发方式 | 只在被 @ 时响应（观察所得）       | 监听所有群消息（已验证）                  |
| 资源操作 | 通过 aily 界面绑定「知识源」（推测） | 通过 lark-cli 直接调用 OpenAPI（已验证） |
| 创建方式 | 在飞书 aily 界面零代码创建      | 由平台运营侧配置部署（系统声明）              |
| 持久化  | 由 aily 平台托管（推测）       | 本地文件系统（已验证）                   |

> 关于「团队智能伙伴只能被 @ 才响应」的原因暂不确定：可能是产品默认配置（只订阅 @ 事件），也可能是创建时未开启「监听所有消息」选项，或受个人账号功能限制。

### 2.4 为什么不采用 PRD 的「团队智能伙伴」方案

PRD 原计划使用飞书 aily「团队智能伙伴」零代码方案，实际采用了 Aily 平台 Agent 方案。真实原因：

1. **团队智能伙伴在个人账号下功能受限**：尝试创建后发现，它们只能在被 @ 时响应，无法实现 PRD 要求的「监听所有群消息并自动处理」这一核心能力。
2. **Aily 平台 Agent 已具备完整能力**：当前 Agent 通过事件订阅实现了全量消息监听，通过 lark-cli 实现了对飞书资源的完整读写，覆盖了 PRD 定义的全部功能。
3. **没有重新搭建的必要**：既然现有 Agent 已跑通核心链路（需求识别 → 表格写入 → 状态跟踪 → 群响应），再回头折腾团队智能伙伴的低代码配置，对 Demo 的价值增量有限。

### 2.5 核心数据流（以需求识别为例）

```
群聊新消息
    ↓
飞书推送事件 → Agent 被唤醒
    ↓
读取本地 status.json 恢复上下文
    ↓
LLM 推理：消息分类 + 实体提取
    ↓
自主决策调用工具
    ↓
lark-cli base +record-create → 多维表格新增任务
lark-cli im +messages-send   → 群里发送确认
    ↓
更新本地 status.json
```

### 2.6 对用户行为的影响

- **核心功能一致**：无论采用哪种机制，最终用户（群内成员）看到的产品行为是一致的——Agent 仍能从群聊中自动抽取需求、维护需求池与决策日志。
- 因此本偏差属于「实现机制（How）」层面的调整，**未改变 PRD 定义的「产品行为（What）」与范围**，无需回改 PRD 的功能需求部分，仅需在技术文档中如实记录差异（本节即承担此职责）。
