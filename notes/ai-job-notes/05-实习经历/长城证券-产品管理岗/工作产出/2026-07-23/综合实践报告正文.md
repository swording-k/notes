# 摘要

本次信息安全综合实践以自主实习的形式，在长城证券金融科技研发中心开展，实习内容主要是金融科技产品的产品研究、操作文档编写与产品运营支持。我本人的专业是信息安全，因此在完成产品与运营工作的同时，也习惯性地从专业角度去观察业务里的一些安全细节。三周里我产出的东西包括：协同平台五个面板的产品介绍视频、商机广场的三版操作文档、一份手拉手统一系统产品研究报告，以及产品地图、知识库和一份产品优化建议清单。因为是信息安全专业的学生，我在写文档和做研究时，会比纯产品视角多留意一些事情，比如敏感信息什么时候该脱敏、不同角色该看到什么、审批流程怎么留痕——但这些是我在实习中"顺带"的思考，我实际做的还是产品和运营的事。所用工具主要有 Markdown、Remotion、PowerPoint、Word、Obsidian、Git 和企业微信微盘。

**关键词：** 信息安全；金融科技；产品研究；操作文档；数据脱敏；权限控制

# 第2章 设计的基本概念和原理

说明一下：这一章写的不是我"设计"了什么安全机制，而是我在做产品研究和写文档的过程中，反复用到的信息安全基础知识。正因为我是这个专业，看业务时会自然往这些原理上靠。

## 2.1 身份认证与私有化部署

平台建在企业微信私有版上。私有化部署意味着组织的通讯录、身份和聊天数据留在企业自己的环境，而不是公有云——这对金融这类强监管行业是基本要求。做产品研究时我理解到，企微私有版在这里其实是"身份底座"：谁能登录、看到哪个组织，由这套私有身份体系决定。这让我联想到课堂讲的身份认证：先确认"你是谁"，再谈后面能干什么。

## 2.2 权限控制与最小权限

平台按角色展示不同任务和数据。商机广场里提报人、认领人、审核员看到的不一样。这种"按角色给不同视图"的做法，本质上就是基于角色的访问控制（RBAC），也是最小权限原则——每个人只看到自己职责范围内、当前确实需要的那部分信息。我在写分角色操作文档时，就是按这个逻辑把三类角色的视图分开写的。

## 2.3 数据脱敏与内容安全

商机广场里的商机常涉及并购、撮合这类高敏感商业信息，联系方式和标的细节不能随便露。产品的做法是列表和卡片上默认只显示部分信息，一方申请对接且对方同意后才展示完整联系方式，也就是"默认脱敏 + 显式授权后披露"。导师审文档时专门点出，撮合确认后联系方式就对对方可见，这一步必须给提示。我在文档里把"部分脱敏 → 同意后看完整"这步写清楚，也是因为专业背景让我对这类细节比较敏感。

## 2.4 操作审计与职责分离

协同申请走多级审批：提交后依次经本部负责人、投行综合部、投行部门负责人审核，最后完成。多级审批对应职责分离——关键操作不能一人拍板，要多方确认。从安全治理看，这条链也是一条审计轨迹：谁何时做了什么决定，系统有记录，出问题能回溯。这和课程里讲的日志与审计对得上。

## 2.5 数据生命周期与终端安全

商机发布可选有效期（30、60、90 天），到期前七天提醒，期满自动下架。这是数据生命周期里"留存期限"的体现。另外入职配电脑时我碰到终端安全：内网机器走软件白名单、最小化安装，连不进内网的只能做外网查阅。换下来的机器带毒，先重装基线再纳入管控。这些在日志里只是"设备问题"，但放到安全框架下看，就是标准的主机加固。

# 第3章 总体设计

## 3.1 实现方法

我这次实习以产品研究和运营支持为主线，具体就是"产品研究 → 操作文档 → 优化建议"这条线。信息安全不是我的工作任务，而是我带进去的视角：每做到一处，我会顺手对照一下课堂原理，看看这个地方在真实业务里是怎么落地的。对一个信息安全学生来说，能这样从头跟一套真实系统，比单点做个小工具收获更大。

## 3.2 技术路线

整体路线分五步：

（1）建立产品认知：搞清楚平台建在企微私有版上，身份和通讯由私有化部署保证，内外网隔离。

（2）做产品研究与文档：跑通商机广场发布、审核、认领、撮合全流程，自截图标，写出操作文档和研究报告。

（3）对照安全原理：在看流程和写文档时，把遇到的脱敏、权限、审批、有效期这些点，和课堂概念对上号。

（4）整理优化建议：把研究和文档里发现的、可改进的点汇总成清单。

（5）沉淀知识库：用产品地图和图谱把概念关系固定下来。

## 3.3 工具链

文档用 Markdown 写，用 Obsidian 维护产品地图和知识库的关系图谱，用 Git 做版本控制，用企业微信微盘在内部传文件（不走明文外发）。视频用 Remotion 渲染，操作文档和报告用 PowerPoint 与 Word。AI 智能体只在公司允许范围内辅助资料归纳和排版，源码和内部数据严格遵守权限管理。

# 第4章 详细设计

## 4.1 主要交付物的内容与结构

这一节说清楚我实际做出来的东西长什么样。

### 4.1.1 协同平台产品介绍视频

五个面板各一段口播视频，约四十秒，用 Remotion 以代码方式定义文案与节奏，渲染成超宽屏 mp4。首页讲平台定位，商机挖掘讲发现企业，协同管理讲协同申请与分润，客户管理讲客户视图，AI 助理讲智能助手。视频面向新人，把"入口在哪、每步点哪"讲清楚。

### 4.1.2 商机广场操作文档

三版，结构不同：全流程版按"发布 → 审核 → 认领 → 撮合"环节讲；分角色版按提报人 / 认领人 / 审核员三种角色讲；补强版十七页，含场景、角色视角和术语收口。每步除了"点哪里"，还补了"填什么、状态什么意思"，并配自截实操图（截图前对敏感字段脱敏）。

### 4.1.3 手拉手统一系统产品研究报告

先写 Markdown 研究稿，讲内部产品逻辑、两类能力、双端布局、统一工作台判断、产品建议；再排成二十一张 Word 正式版，最后精简成十六页最终发送版。公开资料部分只引用年报和官网口径，没登录也没试用外部系统。

### 4.1.4 产品优化建议清单

四条，都带页面或流程依据：移动端入口收敛、敏感信息展示时机、有效期提醒、PC 首页商机广场面板说明。发给导师评估优先级。

## 4.2 交付物里顺带做的安全视角观察

这里列的不是我"设计"的安全功能，而是我在做上面这些交付物时，作为信息安全学生多留意到的几点。它们帮我把手头的文档写得更严谨，但不是我的工作岗位要求。

（1）脱敏与披露时机：商机联系方式默认脱敏、同意对接后才完整显示。我在文档里把这步写清楚，并建议撮合披露时给明确提示——这是内容安全和告知同意的体现。

（2）角色与权限视图：三类角色看到不同内容，对应 RBAC 和最小权限。分角色文档就是按这个逻辑组织的。

（3）审批与审计链：协同申请多级审批，对应职责分离，也形成审计轨迹。

（4）有效期与留存：发布选有效期、到期自动下架，对应数据生命周期的留存控制。我在文档里补了"到期前七天提醒、期满下架"的说明。

（5）入口收敛：移动端把"协同申请"和"协同申请审批"收进一个"协同管理"入口、按权限展示，等于收窄功能暴露面。这一点我写进了优化建议。

# 第6章 简要的使用说明

## 6.1 操作文档怎么用

商机广场操作文档是给新人和相关业务同事看的。全流程版适合第一次接触的人，按"发布 → 审核 → 认领 → 撮合"的顺序走一遍；分角色版适合已经知道自己是哪类角色的人，直接看自己的操作路径；补强版是给导师和老员工做核对用的，内容最全。看的时候注意每步旁边的状态说明，比如审核有通过、驳回、待审核，对接有同意、拒绝，别只盯着主路径。

## 6.2 协同平台与商机广场的基本路径

协同平台（PC 端）的核心是协同申请与分润：在系统里发起协同、总部接单、按规则分润。商机广场（手机端）的核心是发布和认领商机：业务人员在外面发现并购或撮合需求，发到广场，专业同事认领，撮合成功后回到 PC 端发起协同。两者目前是两类入口，长期可能收敛到手拉手统一系统。报告里对这些路径都画了图，对照着看不容易混。

## 6.3 研究报告与建议清单怎么用

研究报告是给团队内部理解产品和做后续规划用的，公开资料部分只引用年报和官网口径，没有登录或试用外部系统。优化建议清单是给导师评估改进优先级的，每一条都写了依据和影响范围，后续如果要落地，会再写成正式的 PRD。

# 第7章 总结

## 7.1 特色

这次实践的特色不在"做了安全"，而在我把信息安全专业的眼睛带进了产品与运营实习。同样看一个"联系方式什么时候显示"，产品同学只看体验，我会先想到内容安全和最小权限。这种视角叠加，让我写的文档比纯产品视角多了安全这一层考量——但它始终是我专业背景带来的附加值，不是我的岗位职责。

## 7.2 经验

第一，框架先行。前两周反复返工，根子都在"框架没想清楚就动手"。后来养成习惯，动手前先把结构想全，拿不准就先和导师对框架，返工明显少了。第二，ToB 产品要站在"让读的人理解、会用"的角度组织内容，不能只堆操作步骤，要考虑角色和业务闭环。第三，带专业视角看业务确实有帮助，但得摆在合适的位置，不能喧宾夺主。

## 7.3 教训

教训也有。一是前期对产品关系理解偏差，把商机广场当成协同平台的前置环节，写了半天发现不对，又返工重来，浪费了不少时间。二是安全细节容易被忽略，像敏感信息展示时机、有效期到期后的状态，都是导师审到第三遍才点出的，说明我对"安全要落到每个字段、每个状态"还不够敏感——尽管我自己就是学这个的。

## 7.4 感受

三周前入职时，我连产品长什么样都看不到；三周后，我已经能独立写出一份产品研究报告，还能从专业角度提几点观察。最大的感受是，课本上那些抽象的原则——私有化、脱敏、最小权限、职责分离——在真实业务里都不是名词解释，而是每天在做的具体决定。能看到它们怎么落地，是这次实习最值的地方；而我自己的本职工作，始终是把产品和运营的事做好。
