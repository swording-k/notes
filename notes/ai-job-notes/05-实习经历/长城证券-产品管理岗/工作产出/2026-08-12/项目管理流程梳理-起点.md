## 三、项目管理实体与关系（基于成熟方案 + 你的指正，定稿）

### 3.1 调研结论：成熟方案怎么做（Jira / 禅道 / Azure DevOps）

| 维度 | 成熟方案做法 | 对我们的启示 |
|------|------------|------------|
| 层级 | Jira/ADO：**Epic → Story(需求) → Task → Subtask**；禅道：发布/计划 → 需求 → 任务 | 需求与任务天然在两个层级，不是一回事 |
| 需求 vs 任务 | Jira：Story=用户视角的"做什么"，Task=不直接对应需求的"怎么做"的工作；禅道：需求 1:N 任务 | 和我们"需求=做什么、任务=怎么做"一致 |
| **Bug** | Jira 把 Bug 作为 work type，与 Task **平级**；禅道列为独立对象但可"转任务" | **Bug 是任务的一种** → 用 `任务.type=缺陷`，不单建实体 ✅（采纳用户判断） |
| **测试用例** | 禅道/ADO 都放**独立"测试"模块**，通过"关联需求"做可追溯（RTM），**不是任务** | v1 **不管理测试用例细节**（Non-goal），但用 `任务.type=测试` 捕获测试工作 |
| 角色 | 禅道把"设计"列为独立对象类型；研发/测试/设计皆资源角色 | 人员表加 `角色` 字段，任务 `type` 对应角色，弱绑定需求 |

> 结论：三家的共识是——**需求、任务是两个实体，用"工作项类型"区分 Bug，测试用例独立管理**。我之前把需求/任务同表的写法违背了这条共识，新版已纠正。

### 3.2 标准实体与必须字段（定稿）

| 实体 | 必须字段 | 说明 |
|------|---------|------|
| **项目 Project** | 项目ID、名称、目标、总负责人、状态、起止时间、成员 | PM 的容器；目标+负责人是"谁为何做"的最小信息 |
| **需求 Requirement** | 需求ID、标题、描述(含业务价值)、**验收标准**、提出人、提出时间、来源、优先级、状态、关联项目 | "做什么 + 做到什么算完"；验收标准是需求与任务的边界 |
| **任务 Task** | 任务ID、标题、描述、**关联需求**(M:N)、`type`(开发/设计/测试/缺陷)、责任人、执行人、状态、起止、预估/实际工时、优先级、所属项目、父任务(自引用) | "怎么做"的执行单元；`type` 把 Bug/设计/测试都收进任务，不另建实体 |
| **工时 Timesheet** | 日期、成员、任务、时长、类型(预估/实际) | 成本与负载量化的最小事实；归属主体是任务 |
| **人员 Member** | 成员名、部门、账号、**角色**(PM/技术负责人/前端/后端/设计/测试)、负责任务/执行任务 | 资源载体；`角色` 解决"设计/测试怎么纳入"的问题 |
| **决策 Decision** | 决策标题、内容、决策人、时间、关联(需求/任务/项目)、状态(提议/已确认/已推翻) | "谁拍板、为什么、何时"的痕，支撑可追溯 |

> **明确不纳入 v1（Non-goals）**：① 测试用例细节（步骤/预期/执行记录）；② 代码提交/Git 关联；③ 发布/版本管理模块。理由：范围控制，当前 agent 价值在"需求→任务→分派→进度"，测试管理是另一学科，留待后续。

### 3.3 需求 ≠ 任务：关系定稿（M:N + 委托链）

```
项目 1:N 需求                需求 M:N 任务（RTM 关联表）
项目 1:N 任务                任务 1:N 子任务（自引用 parent_task）
任务.责任人(A, 初始=小队长) ─┐
任务.执行人(R, 实际做的人)  ─┴─ 人员(带角色)
任务 1:N 工时 ── 人员 1:N 工时
需求/任务/项目 1:N 决策（虚线关联）
```

- **需求 M:N 任务**：你的例子——10 条需求，PM 从 8 条提取任务，或 1 需求拆多任务，或 1 任务服务多需求——全部由关联表表达，不合并实体。
- **两段式委托（责任人 vs 执行人）**：对应你说的"PM → 前后端小队长 → 具体人"。责任人=问责方（RACI 的 A，初始是小队长），执行人=做事方（RACI 的 R，小队长再分派时填）。群聊 @一人 默认两者同写；@小队长 后再细化，则责任人在前、执行人在后。

### 3.4 测试用例要不要管（你的问题，结论在此）
- **是什么**：测试用例 = 验证某需求是否按验收标准工作的具体步骤+预期结果+执行记录，由测试人员维护。
- **成熟方案**：独立测试模块，关联需求做追溯，不混进任务流。
- **我们的决定（v1 Non-goal）**：**不管理测试用例细节**。但"测试"作为一类工作，用 `任务.type=测试` 捕获（谁、何时做测试）；测试发现的问题 → `任务.type=缺陷`。既纳入测试角色，又不把测试管理复杂度拖进 v1。

### 3.5 角色怎么纳入（设计/测试）
- 人员表加 `角色` 字段：PM / 技术负责人(小队长) / 前端 / 后端 / 设计 / 测试。
- 任务 `type` 与角色对应：开发任务→前后端；设计任务→设计；测试任务→测试；缺陷→谁修谁接。
- 设计/测试"与需求任务无强绑定"→ 用 `任务.关联需求` 表达弱绑定（可关联，也可独立）。

### 3.6 开发模式（敏捷 / 瀑布）如何影响我们的 PM 模型

> 用户提问：敏捷、瀑布都没讲，不同方式对应的项目管理不同吗？答：**开发模式决定的是"节奏与需求如何处理"，底层实体（项目/需求/任务/工时/人员/决策）是共用的，变的是容器与流程规则。**

| 维度 | 瀑布 Waterfall | 敏捷 Agile（Scrum / Kanban） |
|------|--------------|----------------------------|
| 需求处理 | upfront 冻结，变更走 CR 流程 | 持续产生，backlog 滚动优先级 |
| 计划 horizon | 一次性总计划 + WBS + 甘特 | 滚动规划，按迭代（2–4 周）承诺 |
| 跟踪单元 | 阶段 / 里程碑 / WBS 任务 | 用户故事 / 任务 + 看板 |
| 变更态度 | 抗拒，变更成本高 | 拥抱，随时调整 |
| 典型角色 | PM 强管控 | PO（产品负责人）+ SM（Scrum Master）+ 自组织团队 |
| 度量指标 | 里程碑偏差 / 完工率 | 速率 Velocity / 燃尽图 / 交付频率 |
| 适用场景 | 需求明确、强监管（核心交易系统）、硬件 | 需求不确定、内部工具 / 互联网（协同平台） |

**对我们实体模型的影响（字段扩展维度）：**
- 选**敏捷**：加 `迭代 Sprint`（时间盒容器，任务挂迭代）+ `backlog 优先级` + `速率` 指标；状态流用 §四.2 的轻量版即可。
- 选**瀑布**：加 `阶段 / 里程碑` + `变更请求 CR`（需求变更不直改，建 CR 关联原需求）+ `基线 / 偏差` 度量。
- **共用部分不变**：项目 / 需求 / 任务（M:N）/ 工时 / 人员（角色）/ 决策 全部照旧；Bug-as-type、测试用例 Non-goal 也不变。

**结论**：模式不同 → PM 的"节奏字段"不同，但核心实体与关系稳定。这正说明我们先把实体拆对（需求≠任务）的价值——换模式只加容器，不推翻结构。

**待团队拍板**：协同平台第3期及日常用**敏捷**还是**瀑布 / 混合**？（建议敏捷：群聊随时冒需求、天然是滚动 backlog；但券商涉及合规的核心系统可能 hybrid。这决定我们是否要加 `迭代` / `CR` 字段。）

## 四、我替你拍板的细节（你说让我定，已决策）

### 4.1 任务颗粒度（最小单位）
- **定义**：任务 = 一个角色能在 **≤1 迭代 / ≤1 周** 内独立完成、可验收的工作单元（按人天估算）。
- **再细**：子任务（自引用 `parent_task`），用于一个任务需多人/多步时拆；子任务也是任务（type 可继承或另设）。
- **红线**：一句话太碎（不要）、整个模块太粗（不要）。

### 4.2 状态流（两套，不强制对齐禅道）
- **需求状态流**：`草稿 → 评审中 → 已采纳 → 研发中 → 已实现(待验收) → 已验收 → 关闭`（+ `已拒绝`）。
- **任务状态流**：`待办 → 进行中 → 待验收/阻塞 → 已完成 → 关闭`。
- **决策**：轻量实体，挂在需求/任务/项目任一下，状态 `提议 / 已确认 / 已推翻`。

### 4.3 委托链落地（责任人 vs 执行人）
- 责任人(问责 A)：对交付负责，初始=小队长（PM 分派时填），可后期转个人。
- 执行人(执行 R)：实际做的人，小队长再分派时填。
- 群聊场景：@一个人 → 默认同写责任人与执行人；@小队长 后再细化 → 责任人在前、执行人在后。

## 五、操作手册式流程（用"协同平台第3期"走一遍）

> 目标：让任何读这份文档的人，能照着把我们的 PM 流程跑通。对应你举的例子。

1. **建项目**：PM 在群里/@Agent 建项目「协同平台第3期」，填目标、总负责人、起止时间。→ 项目状态=推进中。
2. **业务交流产需求**：PM 与业务方（如杨一骢、各条线）沟通，沉淀 **10 条需求**进需求池，每条含验收标准、优先级。→ 需求状态=草稿→评审中。
3. **评审采纳**：团队评审，8 条采纳、2 条暂缓。→ 采纳的需求=已采纳；暂缓的=已拒绝/挂起。
4. **PM 提取任务**：PM 从 8 条需求提取任务。例：需求A"商机广场支持批量导入"→拆 后端接口任务、前端页面任务、联调测试任务 3 个；需求B"协同分润规则可视化"→1 个后端任务。`任务.关联需求` 指向对应需求（**M:N**：联调测试任务可能同时服务需求A和另一需求）。`任务.type` 分别=开发/开发/测试。
5. **派小队长**：PM 把任务 @给前后端小队长（技术负责人）。此时 `责任人=小队长`，状态=待办。
6. **小队长细分派**：小队长再分给具体人（如 @张三 做后端接口）。此时 `执行人=张三`，状态=进行中（开工填报工时）。
7. **工时**：张三每天在群里/@Agent 报工时，落在工时表（任务+人+日期+时长，区分预估/实际）。
8. **决策留存**：讨论中"分润比例定为 X%"→Agent 识别"就这么定了"→记一条决策，关联对应需求。
9. **完成验收**：任务做完→已完成；需求下所有任务完成→需求=已实现(待验收)→验收通过→已验收/关闭。
10. **测试与缺陷**：测试人员拿 `任务.type=测试` 执行（v1 不管理用例细节，只记"谁何时做了测试"）；发现问题→建 `任务.type=缺陷` 关联原需求/任务，走修复闭环。
