## 1. 核心概念纠偏（最关键）

**需求 ≠ 任务。** 这是之前版本犯的概念错误（曾把两者写成"同一张表"），必须纠正：

- **需求（Requirement）** = **做什么 / 为什么**（what / why），含验收标准。回答"我们要解决什么业务问题、做到什么程度算完"。
- **任务（Task）** = **怎么做**（how），具体的执行工作单元。回答"由谁、花多少工时、把需求落地"。

**两者关系是 M:N（多对多），不是同表、也不是简单 1:N：**

- 一个需求可以拆成多个任务（如"商机广场批量导入"→ 后端接口 + 前端页面 + 联调测试 3 个任务）。
- 一个任务可以服务多个需求（如"通用鉴权改造"同时支撑 3 条需求）。
- 用 **需求-任务关联（RTM，Requirement Traceability Matrix）** 表达，绝不把需求塞进任务表、或反之。
  - **实现说明（重要）**：在飞书多维表格中，M:N **不需要物理独立建表**——直接用「双向关联记录」字段即可（需求表加"关联任务"、任务表加"关联需求"，飞书自动维护多对多）。RTM 是这个概念的名称，不必额外建一张"关联表"。本图此前把 RTM 画成独立框仅为示意，实际落地是关联字段。

> 为什么重要：流程讲不清、验证数据不客观，根子都在这个错误。拆对实体后，验证才能精确到"每条需求是否被任务覆盖""M:N 关联是否完整"。

### 2.7 容器：瀑布与敏捷（hybrid 双容器）

| 容器                   | 字段               | 说明                    |
| -------------------- | ---------------- | --------------------- |
| 里程碑 / 阶段（瀑布）         | 名称 / 门禁条件 / 关联项目 | 长城长大版本走阶段门禁 + 变更请求 CR |
| Sprint / Backlog（敏捷） | 周期 / 目标 / 关联任务   | 日常迭代、加功能、修 bug 走这里    |

> **关键结论**：底层实体（项目/需求/任务 M:N/工时/人员/决策）对两种模式**完全共用**，变的只是"容器"。换开发模式只加容器，不推翻结构。

## 3. 关键规则（实现时必须遵守）

1. **Bug = 任务.type=缺陷**：不单建 Bug 实体。测试 / 用户发现的问题 → 建一条 type=缺陷 的任务，关联原需求/任务，走修复闭环。
2. **测试用例 v1 不管理细节（Non-goal）**：测试用例（步骤/预期/执行记录）是另一学科，不进 v1。"测试"作为一类**工作**，用 `任务.type=测试` 捕获（谁、何时做了测试）；测试发现的问题 → `任务.type=缺陷`。
3. **设计 / 测试角色弱绑定需求**：人员表用 `角色` 字段纳入；设计/测试任务可 `关联需求`，也可独立。
4. **需求与任务无强绑定关键词**：靠**流程阶段 + 创建人**区分——业务方/PM 建需求，PM/技术负责人建任务。Agent 不应靠某个词判定，而靠上下文（谁提的、在谈什么）。
5. **双负责人**：责任人（问责，初始=小队长）与执行人（实际，小队长细分派时填）是两个字段。群聊 @一人 默认同写；@小队长后再细化则责任人在前、执行人在后。

## 4. 状态流（两套，不强制对齐禅道）

### 4.1 需求状态流

`草稿 → 评审中 → 已采纳 → 研发中 → 已实现(待验收) → 已验收 → 关闭`（+ `已拒绝`）

### 4.2 任务状态流

`待办 → 进行中 → 待验收 / 阻塞 → 已完成 → 关闭`

### 4.3 决策状态

`提议 → 已确认 / 已推翻`

---

## 5. 操作手册（用「协同平台第3期」走一遍）

> 目的：让任何人照着能把流程跑通。对应真实委托链：业务方 → PM → 前后端小队长 → 具体人。

1. **建项目**：PM 建项目「协同平台第3期」，填目标、总负责人、起止、模式（混合）。状态=推进中。
2. **业务交流产需求**：PM 与业务方沟通，沉淀 **10 条需求** 进需求池，每条含验收标准、优先级。状态=草稿→评审中。
3. **评审采纳**：团队评审，8 条采纳、2 条暂缓。采纳=已采纳；暂缓=已拒绝/挂起。
4. **PM 提取任务**：从 8 条需求提取任务。例：需求A「商机广场批量导入」→ 拆 后端接口 / 前端页面 / 联调测试 3 个任务（`type`=开发/开发/测试）；需求B「分润规则可视化」→ 1 个后端任务。`关联需求` 指向对应需求（**M:N**：联调测试任务可能同时服务需求A 和另一需求）。
5. **派小队长**：PM 把任务 @前后端小队长。此时 `责任人=小队长`，状态=待办。
6. **小队长细分派**：小队长再分给具体人（@张三 做后端接口）。此时 `执行人=张三`，状态=进行中（开工填报预估/实际工时）。
7. **工时**：张三每天报工时，落在工时表（任务+人+日期+时长，区分预估/实际）。
8. **决策留存**：讨论中"分润比例定为 X%" → Agent 识别收敛信号 → 记一条决策，关联对应需求。
9. **完成验收**：任务做完→已完成；需求下所有任务完成→需求=已实现(待验收)→验收通过→已验收/关闭。
10. **测试与缺陷**：测试人员用 `任务.type=测试` 执行（v1 不管理用例细节，只记"谁何时做了测试"）；发现问题→建 `任务.type=缺陷` 关联原需求/任务，走修复闭环。

## 6. Non-goals（v1 不做）

- 测试用例细节管理（步骤/预期/执行记录）
- 代码提交 / Git 关联
- 发布与版本管理模块
- 变更请求(CR)全流程自动化（仅保留"大版本走阶段门禁"的概念，不自动化审批流）
- 子任务无限嵌套（仅一层 `父任务` 自引用）

## 7. 给 Agent 的群聊→实体映射规则（实现参考）

> 这部分是给 Agent 的系统提示用的，说明"群里一句话该落到哪个实体"。

| 群聊信号               | 映射动作                   | 落到实体  |
| ------------------ | ---------------------- | ----- |
| "开个新项目 / 第X期"      | 建项目 + 填模式/负责人          | 项目    |
| 业务方描述痛点 / "希望系统能…" | 建需求 + 填验收标准/优先级        | 需求    |
| "就这么定了 / 确定按X做"    | 建决策 + 关联当前上下文对象        | 决策    |
| "把这个拆成…任务 / 谁来做"   | 建任务 + 关联需求 + 写责任人/执行人  | 任务    |
| 报 "今天做了X小时"        | 追加工时记录                 | 工时    |
| 提 bug / "这里有问题"    | 建 `type=缺陷` 任务 + 关联原对象 | 任务    |
| @Agent "改状态为已完成"   | 更新任务/需求状态              | 任务/需求 |
| 普通闲聊 / 无项目含义       | **忽略，不建任何记录**          | —     |

> 判定优先级：先识别"是否在谈项目相关的事"（防闲聊），再判定落在哪个实体；需求与任务靠"上下文 + 创建人角色"区分，不靠关键词硬匹配。
