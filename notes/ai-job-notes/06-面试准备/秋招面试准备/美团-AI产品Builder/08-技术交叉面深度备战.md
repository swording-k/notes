## 一、FitGenius 源码拆解（技术原理）

### 1. 整体架构：三个角色，一条数据流

```
用户说话 ──► AIService.chat()
                │
                ├─ 拼 system prompt（含：动作库清单、当前计划、任务说明）
                ├─ 调大模型（流式 SSE）
                ├─ extractJSONObject() 从废话里抠出纯 JSON
                ├─ parseActionCommand() 解析成 AIActionCommand
                │
                ├─ 如果是 JSON 指令 → 返回 command（上层执行，改计划）
                └─ 否则 → 返回普通文本（聊天答疑）
```

三个文件分工：
- **AIService.swift**：AI 总调度（发请求、抠 JSON、解析、兜底、多模态）。核心大脑。
- **ChatMessage.swift**：`AIActionCommand` 数据结构定义（3 种指令的标准格式）。
- **AIResponseFormatter.swift**：纯文本显示格式化（去 Markdown 符号），技术含量低，不是核心。

### 2. 核心思想①：结构化输出约束（让 AI 吐出可解析的东西）

**问题**：大模型返回的是自然语言，可能夹带"根据渐进超负荷原则…```json{...}```"这种废话，直接 `JSONDecoder().decode` 必崩。

**解法三层**：
- **第一层 prompt 强约束**：system prompt 里写死"必须返回纯 JSON，不要 Markdown 围栏"（`languagePolicy.actionJSONExample` + "Important: if returning JSON, return raw JSON only"）。
- **第二层 extractJSONObject（关键兜底，AIService.swift:627）**：一段括号匹配算法，从任意文本里抠出第一个合法的 `{...}`：
  ```
  从第一个 "{" 开始扫描：
    - 遇到引号 " 进入字符串态（inString），字符串内的 { } 不计数
    - 遇到转义 \ 跳过下一个字符
    - 不在字符串时，{ 深度+1，} 深度-1
    - 深度归 0 的那个 } 就是结尾 → 截断返回
  ```
  这就是容错解析：模型哪怕前后写废话、包了 ```json，也能抠出真 JSON。
- **第三层 cleanMarkdownCodeBlock**：去掉 ```json / ``` 围栏的兜底。

> 面试可讲："大模型输出不稳定，我做法是 prompt 强约束 + 正则抠 JSON + 失败降级三件套，这是 AI 应用落地的工程基本功。"

### 3. 核心思想②：受控指令集"锁爆炸半径"（你文档里写的"锁爆炸半径"）

`AIActionCommand`（ChatMessage.swift:33）只有 **3 种 type**：
```swift
let type: String // "update_plan", "add_exercise", "remove_exercise"
```
每个 Action 带 `day / oldExercise / newExercise / exerciseName / sets / reps / weight / reason`。

**关键设计**：`chat()` 方法（AIService.swift:415）返回的是 `(response: String, command: AIActionCommand?)`——**AI 不直接改计划，只返回一个"指令对象"，由上层代码去执行**。这意味着：
- AI 能做的操作被锁死在这 3 种 + 固定字段里；
- 它不能"自由发挥"去改数据库的任意字段、不能执行删除以外更危险的操作；
- 这就是"爆炸半径"控制：即使模型抽风，最坏也只是"加/删/改某个动作"，不会把整个计划搞乱。

> 这和你之前 07 文档里写的"AI 改计划仅 3 固定指令锁爆炸半径"是同一个点，现在有了源码佐证。

### 4. 核心思想③：动作库注入（轻量 RAG / 检索增强）

`buildExerciseCatalogSection()`（AIService.swift:380）：把动作库前 400 个名字拼进 system prompt，指令模型"优先从这份清单挑动作、原样用英文动作名"。

`matchTemplate()`（AIService.swift:402）：解析后，把 AI 返回的动作名**回连**到 ExerciseTemplate，打通 GIF 演示与详情。

这本质是一个**简化版 RAG**：不向量检索，而是"把相关知识直接塞进上下文"，让模型基于真实私有数据生成，避免它编出不存在的动作。

### 5. 核心思想④：防御性降级（一个值得讲的设计演进）

`generateInitialPlan()`：解析失败 → 用 `fallbackPlan()`（本地固定增肌模板）。

但 `regeneratePlan()`（AIService.swift:363）**特意改了行为**——注释写得很清楚：
> 解析失败时【不再】静默落一个不相关的兜底计划——那会让用户误以为"已按我的要求改好"，实际却是个固定增肌模板，表现就是"乱改/没按我改"。改为抛出错误，由上层提示重试并保留旧计划。

**这是个很有价值的工程判断**：静默兜底看似"不崩"，实则"欺骗用户"。改成抛错 + 保留旧计划，牺牲了"表面不报错"，换来了"用户信任 + 状态正确"。面试讲这个，显你有产品 + 工程的双重视角。

### 6. 模型路由 + 多模态

- **双模式**（AIService.swift:183）：国内直连（用户自有 Key，直连 provider OpenAI 兼容端点）/ 后端代理（Vercel/CloudBase，session token）。`effectiveTextModel` 做别名→真名映射。
- **多模态入口**：`dietChatWithImages`（视觉，base64 压图避免超 100KB 限制）、`analyzeFitnessMedia`（视频，>10MB 自动压缩、>20MB 硬拦截）、`enrichFormFeedback`（骨架图 + 本地规则评分结合）。
- 这些说明 FitGenius 不是"调个 chat API 就完事"，而是处理了真实的多模态工程问题（图片压缩、视频上限、流式解析）。

### 7. FitGenius 的"Agent 思想"一句话总结

> FitGenius 用"大模型 + 结构化指令约束 + 3 种固定操作 + 动作库回连 + 防御性降级"，实现了一个**简化版受控 Agent**：LLM 在其中扮演"决策者"，但决策空间被严格限定，所有危险操作都被沙箱化。这就是 Agent 思想在移动端 AI 产品里的落地。

### 1. 真实架构：双模式运行（关键事实）

`runtime.py` 第 72-76 行：
```python
agent = (
    HarnessAgent(HarnessGateway(...))   # HARNESS_ENABLED=true（默认）

    else Agent(OpenAiCompatibleLlm(...), tools)  # 自研兜底
```

### 3. Loop（harness 原生提供；agent.py 只是兜底）

`agent.py` 里的 `Agent.handle()`（agent.py:21）是一个标准 **ReAct 循环**（Reasoning + Acting），它是**关闭 harness 时的兜底**：
```
messages = history + 用户消息
for iteration in range(max_iterations=4):   # 最多 4 轮
    1. response = llm.complete(messages, tools)   # 思考：LLM 决定下一步
    2. if response.final_text: return             # 任务完成，直接回答案
    3. result = tools.execute(response.tool_name, response.arguments, context)  # 行动：调工具
    4. messages += assistant_message(tool_call)    # 观察：把"我调了什么 + 结果"塞回上下文
       messages += tool_result
# 超过 4 轮 → 返回"操作步骤过多，请拆分后重试"
```
**默认 harness 模式下，这个 Loop 是 DeepSeek Harness 原生跑的**，不需要你写；`agent.py` 这套自研循环只是保险。

**细节亮点（面试可聊）**：
- OpenAI-compatible 工具调用是"三消息交换"：assistant 的 tool_call + 带 tool_call_id 的 tool 结果（agent.py:38-63）。
- DeepSeek 推理模型需要回显 `reasoning_content`，否则 HTTP 400（agent.py:52）——这是真实踩过的坑，显你对接过不同模型。

### 4. Harness —— 这才是项目真正的底座（DeepSeek Harness）

**核心理念 `Model + Harness = Agent`**：模型只负责"思考/生成"，把 Agent 拆成可插拔零件（循环、记忆、工具、权限、连接）交给 Harness 统一编排。类比：Model 是发动机，Harness 是整车底盘+变速箱——你买发动机（任意 LLM），整车怎么跑由 Harness 决定。官方仓库 `github.com/deepseek-ai/deepseek-harness`，⭐38k+，MIT，TypeScript。

**架构哲学"一切皆插件"（Cordis 架构）**：底层是 Cordis 依赖注入/插件框架。人格、工具、记忆、连接、审计全是插件，通过 `inject` 服务键组合，换团队/换配置不改骨架；`dsh plugin add` 一键装社区插件，生态已有 700+ 插件。

**四个原生企业级能力**（对比"自研单进程"的短板）：

| 能力 | 是什么 | 为什么企业级重要 |
|---|---|---|
| **Agent Loop** | 原生智能体循环（think→act→observe），不是你自己写 while | 稳定、可观测、可中断 |
| **跨轮会话记忆** | 长驻 + 持久化（JSONL/SQLite）+ 主动落盘 | 解决"说了上句忘下句"，指代解析增强 |
| **工具编排 + 插件** | 工具注册表、权限门控 | 能力可组合、可复用、可控 |
| **子 Agent + 审计日志** | 子代理并行、逐轮验证、会话健康检查 | 可追溯、可并行、合规 |

**你的自研 Harness 层（`harness_bridge.py`）**：`ALLOWED_TOOLS`（harness_bridge.py:18）是一个 frozenset 白名单，只暴露 16 个项目管理操作；`ProjectManagementBridge.handle_json()` 里 `if name not in ALLOWED_TOOLS: raise ValueError(...)`，这就是"沙箱本质 + 锁爆炸半径"——Agent 想调什么必须先过白名单，异常全部捕获兜底，绝不崩溃暴露给上层。

### 5. 你踩过的真实坑：headless 一发即弃 vs 长驻 + M1 探针（加分项）

当前 `harness_gateway.py` 调 harness 用的是 `dsh --profile headless` **每来一条消息起一个一次性进程**，历史对话由 Python 层手动拼进 prompt（`_render_history`）。这是我当初踩过的坑——headless 一发即弃、零跨条记忆，曾导致"上下文垮"（`第3期指哪个项目`全忘）。
- **怎么解决的**：先用手动注入历史顶上（保证可用），同时写了 **M1 探针**用 `dsh-jsonrpc-agent` + JSONL 会话持久化验证**原生跨轮记忆确实生效**（"第3期=飞书PM机器人第3期"跨轮指代成功），结论是"harness 的会话记忆 + 主动落盘（`项目备忘.md`）是双保险，这才是企业级底座该有的样子，也是我把 PM 智能体迁到 harness 的理由"。
- 这个"踩过坑、做过对照实验、有数据结论"的叙事，比单纯背概念值钱得多。

### 8. 飞书 PM Agent 面试三段话术（直接背）

**被问"你这个智能体是怎么实现的？"**
> "我没有从零造 Agent 内核，而是基于 DeepSeek Harness（`Model + Harness = Agent` 理念）来搭。最难的部分——Agent 循环、跨轮记忆、工具编排——都是 harness 原生提供的；我做的是一层领域插件：把项目管理的 14 个操作封装成工具，再配一个很薄的 Python 桥接飞书长连接。我特别做了两件事保证它'可落地'：一是工具白名单锁爆炸半径，AI 只能调我允许的 PM 操作；二是字段白名单 + 写入前三核实，保证多维表格写得准、不串数据。"

**被问"为什么选 harness，而不是纯自研？"**
> "因为我踩过坑。一开始用 harness 的 headless 一发即弃模式，发现每条消息起新进程、跨轮记忆用不上，'第3期指哪个项目'这种指代全垮。我写了探针用它的长驻 JSON-RPC + JSONL 持久化验证原生记忆确实生效，结论是企业级智能体必须长驻。自研一个带记忆、审计、插件化的 Agent 内核成本极高，而 harness 38k 星、生态成熟，把领域约束做成插件就能复用——所以选底座、自己只做领域层，是更聪明的分工。"

**被问"Agent 底座和普通调 API 有什么区别？"**
> "普通调 API 是'一发即弃'：你拼个 prompt 发过去，拿个回答，下次啥都不记得，工具调用要自己写 if-else。Agent 底座（harness 这类）把四件事标准化了——① 原生 Agent Loop（不用自己写循环和重试）；② server-side 跨轮记忆（指代、上下文不垮）；③ 工具/插件编排（能力可组合、可控、可审计）；④ 子代理与审计（可并行、可追溯）。本质区别是：调 API 是'用模型'，Agent 底座是'给模型一套能持续干活的运行环境'。"

> ⚠️ 红线：① 别把"自研兜底路径（`agent.py` 那个 Agent 类）"说成项目主体——面试官若看过你 GitHub 问"harness 和你的 Agent 类什么关系"，要能答"默认走 harness，Agent 类是关闭 harness 时的兜底"。② 别编没做过的：harness 的"子代理/审计"你只是调研过生态、没在 PM 项目里实际接，讲到这层要说"生态里有、我评估过、但 PM 项目当前主要用了记忆+工具两层"。③ 技术面也要回扣产品：讲完原理补一句"这些工程取舍最终是为了让非技术团队零代码就能用上 PM 智能体"。

## 三、基础概念详解（背熟版，用大白话说）

### 1. MCP（Model Context Protocol）
- **是什么**：AI 连接外部工具/数据的**标准协议**（类比 USB-C——统一接口，不用每个工具写一套适配）。
- **vs CLI**：CLI 是"文本命令行入口"（人敲命令）；MCP 是"模型调工具的协议层"。CLI 只是 MCP 可能调用的一种执行入口，不是一回事。
- **面试答法**："MCP 让 Agent 用统一方式接数据库、API、文件系统，不用为每个工具单独开发，是 Agent 工程化的关键协议。"

### 2. Agent / LLM Agent（智能体）
- **是什么**：能**自主决策下一步**的系统 = 大模型（大脑）+ 工具调用（手）+ 记忆（上下文）+ 规划（Loop）。不是单纯调一次 API 出文本。
- **vs 普通调用**：普通调用 = 你问它答；Agent = 它自己"想→做→看结果→再想"，直到干完。
- **你俩项目的例子**：飞书 PM Agent 是完整 Agent（Loop + 工具）；FitGenius 是简化受控 Agent（JSON 指令 + 锁爆炸半径）。

### 3. Function Calling / Tool Use（工具调用）
- 大模型输出一种特殊格式（如 `tool_calls`），声明"我要调 XX 工具、参数是 YY"，由程序去执行。是 Agent "动手"的机制。
- 飞书 agent.py 里 `response.tool_name + response.arguments` 就是 Function Calling 的结果。

### 4. RAG（检索增强生成）
- **问题**：模型不知道你的私有/最新知识。
- **解法**：先把相关知识检索出来，塞进 prompt 再让模型答。
- **你项目里的轻量版**：FitGenius 的"动作库注入"（直接把动作名塞进 prompt）是 RAG 的极简形态——不向量检索，但思想一致（用私有知识约束生成）。

### 5. 结构化输出 / 提示词工程
- 让模型按固定 JSON schema 输出，方便程序解析（见 FitGenius extractJSONObject）。
- 提示词工程 = 通过精心设计 system prompt 引导模型行为（FitGenius 的"8 条训练计划规则"就是提示词工程）。

### 6. 微调 vs 提示词 vs RAG（怎么选）
- **优先提示词 + 工具调用**：成本低、快、可逆。绝大多数场景够。
- **RAG**：知识私有/频繁更新（FAQ、文档问答）。
- **微调**：只有任务高度专用、数据充足、且前两者不行才考虑（成本高、不可逆）。
- 面试答法："我默认先提示词解决问题，知识私有用 RAG，微调是最后手段。"

### 7. 多轮对话状态管理
- 怎么让 AI 记得上下文：FitGenius 用 `ChatMessage` 结构 + `serializePlanToContext` 把当前计划序列化进 prompt；飞书用 `messages` 列表累积。
- 核心：上下文不是无限堆，要"精炼当前状态"喂给模型（FitGenius 的 planContext 就是这个）。

## 七、加面高频：场景设计题 & 效果验证题（附逐字稿）

> 这两类题是"产品+工程"综合题，不背概念、考你**真动手 Builder 的思路**。下面逐字稿全部扣你真实项目（飞书 harness 白名单 / FitGenius 防崩），照着改口吻即可，别硬背。

### 1. 场景设计题（最可能被甩的场景）

**面试官可能问**：
> "假如让你给商家做一个 AI 经营助手（自动回复顾客咨询 / 辅助经营），你从前端到模型怎么搭一个最小可用版本？"

**答题顺序（先砍范围，再分层讲——显你懂 MVP，不会一上来画大饼）**：

1. **先定 MVP 边界**：不做"全功能 Agent"，先做"顾客常见问题自动回复 + 不确定就转人工"。价值闭环最小、风险最低。
2. **前端**：在商家后台嵌一个轻量对话卡片，用 **SSE 流式**展示回答（边生成边出字，体验像打字），不另起 App。
3. **模型层**：大模型做意图识别 + 生成；**小模型/规则做兜底**（高频确定性问题如"营业时间"直接规则答，省成本降延迟）。
4. **工具层（你的亮点，复用飞书经验）**：把"查订单 / 查菜单 / 改预约 / 退款申请"封装成**受限工具白名单**，Agent 只能调这几个；**凡是动资金、改状态的操作必须二次确认**——这就是我飞书项目里"白名单 + 锁爆炸半径"的思想，防 Agent 乱动商家后台。
5. **结构化输出**：和 FitGenius 一样，强制 **function calling / JSON**，模型返回的是"调用哪个工具 + 参数"，不是自由文本，格式稳、不会崩。
6. **降级**：模型挂了或置信度低 → 直接转人工 + 留一句"正在为您转接"，绝不瞎编。

**可直接讲的逐字稿**：
> "我会先把这个助手砍到一个最小可用版本：只做顾客常见问题自动回复，不确定的转人工，这样价值闭环最小、风险最低。前端我会在商家后台嵌一个对话卡片，用 SSE 流式展示，不用另起 App。模型上，大模型负责意图识别和生成，但像'营业时间'这种高频确定问题我用规则或小模型兜底，省成本也降延迟。最关键的是工具层——我会把'查订单、查菜单、改预约、退款'封装成受限工具白名单，Agent 只能调这几个，而且凡是动资金、改状态的操作必须二次确认，这其实是我做飞书 PM 智能体时的核心思路，叫'锁爆炸半径'，防止 Agent 乱动后台。模型输出我强制 function calling，让它返回'调哪个工具+参数'而不是自由文本，格式稳、不会崩。最后留好降级：模型挂了或没把握就转人工，绝不瞎编。这一套我飞书和 FitGenius 两个项目都真实落地过，所以讲起来不是空想。"

### 2. 效果验证题

**面试官可能问**：
> "你怎么判断一个 AI 功能到底好不好用？怎么验证？"

**答题框架（分两层指标 + 三种方法，最后回扣你的短板补救）**：

1. **两类指标分开看**：
   - **离线模型质量**：格式合规率、幻觉率、回答准确率——用测试集 + 人工标注抽样算。
   - **在线业务效果**：回复解决率、人工接管率、顾客满意度（CSAT）、响应时长，以及对 GMV/转化的影响。
2. **三种验证方法**：
   - **小流量灰度 AB**：先放 5% 商家，看接管率/满意度有没有变好，再全量。
   - **LLM-as-judge + 人工抽检**：用强模型先初筛大量对话打分，人工只抽检疑难样本，提效率。
   - **bad case 库回归**：把每次失败案例收进评测集，每次迭代都跑一遍，确保不退化。
3. **健康度监控**：把"人工接管率"当核心健康指标——突然升高就说明模型出问题，立刻告警。

**可直接讲的逐字稿**：
> "我会分两层看。一层是模型质量，比如格式合规率、幻觉率、准确率，用测试集加人工标注抽样来算；另一层是业务效果，比如回复解决率、人工接管率、顾客满意度、还有对 GMV 的影响——光模型分高没用，得看商家和顾客买不买账。方法上，我会先小流量灰度，放 5% 的商家做 AB，确认接管率降了、满意度升了再扩；评测用'强模型初筛 + 人工抽检'提效率；更重要的是建一个 bad case 库，每次迭代都跑回归，防止越改越差。上线后我把'人工接管率'当健康度红线，一突增就告警。坦白说，我之前项目多是种子用户和内部工具，缺海量用户的经验，所以我会特别倚重灰度 + 数据驱动迭代这套方法来补，而不是凭感觉判断好不好用。"

> 这句"坦白缺规模化经验"是**主动亮短板 + 给解法**，比被问到再招架更稳，也显你诚实有方法论。

### 3. 一句话防坑

场景题和验证题，面试官看的不是"你答得多完美"，而是**有没有'先定义边界、再分层落地、留降级、用数据说话'的 Builder 思维**。你把上面两段的"砍 MVP + 白名单锁爆炸半径 + 结构化输出 + 降级"和"两层指标 + 灰度 + bad case 回归"讲顺，就超出了大多数纯产品候选——因为他们讲不出工程细节。

- 重复业务面已问过的 AI 直播 / 商家 Agent 宏观问题 → 这场是技术深挖，宏观题该在业务面聊完。

### 一句话

这场反问的核心原则：**问"怎么干"，不问"什么条件"**。挑问题 1（必问）+ 问题 2（想深挖就问）就够了，自然、显诚意、不卑不亢。

## 九、Agent 范式知识题（ReAct 及对比）—— 交叉面真实缺口，2026-09-23 补

> ⚠️ **这节是补锅。** 前面八节偏重写"项目技术拆解"（一、二节）和"场景设计题"（七节），**没有系统写 Agent 范式这类通用知识题**。四面（技术交叉面）被问到「ReAct 的优缺点？除了 ReAct 还有哪些框架/范式？」——没答上来，这是准备的缺口，现在补上。
> **先正名**：这里的 **ReAct 是 Agent 范式（Reasoning + Acting）**，不是前端框架 React。别再搞混——很多人栽就栽在把它当成前端 React 去答。

### 1. ReAct 是什么（30 秒定义，背）

**ReAct = Reasoning（推理）+ Acting（行动）**，核心是一个循环：

**Thought**（我下一步该干嘛）→ **Action**（调某个工具）→ **Observation**（拿到工具返回）→ 回到 Thought → …… → 直到 **Answer**（给最终回答）

一句话定义（面试直接说）：
> "ReAct 就是让模型**边想边做**：每一步先输出一段思考（Thought），再决定调哪个工具（Action），拿到结果（Observation）后再想下一步，循环直到任务完成。"

**你其实做过，只是没对上术语（关键，别慌）**：
- 飞书 PM Agent 里，DeepSeek Harness 原生跑的那个 loop 就是 ReAct（第二节第 3 点写过）；`agent.py:21` 的 `Agent.handle()` 那个最多 4 轮的循环也是标准 ReAct。
- 所以交叉面答不上，**不是你不会，是"做过的事"和"这个名词"没连上线**。

### 2. ReAct 的优缺点（被问"优缺点"直接照这个答）

**优点**：
1. **可解释 / 可 debug**：Thought 是明文，能看到它每步为什么这么干 → 你飞书项目的日志能审计全靠这个。
2. **能纠错**：工具返回空/错，下一轮可以换工具或改参数重试（纯 CoT 只能一条路走到黑）。
3. **按需取数，省 prompt**：不用一次性把所有资料塞进上下文，用到才调。
4. **天然适配工具白名单**：Action 这一步就是挂权限校验的位置（你 `harness_bridge.py` 的 `ALLOWED_TOOLS` 正是卡在这）。

**缺点**（答得出缺点才是加分项，多数人只想得到优点）：
1. **串行、慢**：一步一调，每轮一次 LLM 往返，延迟叠加 → 你飞书项目限"最多 4 步"就是在控这个。
2. **容易陷入死循环**：模型反复调同一个工具出不来 → 你那句"操作步骤过多，请拆分后重试"就是在防它。
3. **上下文膨胀**：Observation 不断回灌，越长越贵、容易超窗 → 所以要上下文压缩 / 事件溯源（DeepSeek Harness 的解法）。
4. **缺全局规划**：只看眼前一步，复杂多步任务容易跑偏 → 这才引出 Plan-and-Execute。
5. **对模型要求高**：小模型容易 Thought 胡编、Action 格式写错。

### 3. 除了 ReAct，还有哪些范式/框架（第二问，必背）

| 范式 | 核心思想 | 优点 | 缺点 | 什么时候用 |
|------|---------|------|------|-----------|
| **CoT（思维链）** | 只推理、不调工具，"想一想再答" | 简单，提升推理 | 拿不到外部信息，易幻觉 | ReAct 的前置基础，纯推理题 |
| **ReAct** | Thought→Action→Observation 循环 | 可解释、能纠错、按需取数 | 串行慢、易死循环、缺全局规划 | 工具少、要可解释、任务中等 |
| **Plan-and-Execute** | 先一次性产出完整计划，再逐步执行，可 replan | 有全局观，适合复杂多步 | 计划错了后面全错，灵活性差 | 步骤多、依赖顺序强 |
| **ReWOO** | 推理时**不看** Observation，一次性把工具调用全写完，再**批量并行**执行 | 并行→快、省 token | 不能按中间结果调整，容错差 | 多个独立工具调用可并行 |
| **Reflexion** | ReAct + 事后反思：失败后写反思存进记忆，下次改进 | 能从失败中学习 | 多一轮 LLM、成本高 | 反复失败、要越做越好 |
| **单次结构化输出（Function Calling 直调）** | 一次 LLM 直接吐结构化调用，不循环 | 快、便宜、爆炸半径小 | 不能多步、不能纠错 | **FitGenius 就是这种** |
| **Multi-Agent** | 编排者 + 多个专家 Agent（规划/检索/编码/评审）分工 | 能拆超复杂任务、可并行 | 成本高、状态同步难、易互相污染 | 超复杂、需多角色协作 |

补充：Multi-Agent 的状态污染问题，正是 DeepSeek Harness 用**事件溯源（Event Sourcing）**去解的（每个 Agent 状态独立投影、互不污染）——这点和你项目直接连得上。

### 4. 怎么选（判断方法，别死记）

按这 4 个问题选，就能答"你为什么这么设计"：
1. **要拿外部数据吗？** 不要 → CoT / 单次结构化输出（FitGenius）；要 → 往下。
2. **要几步？** 1 步 → 单次结构化输出；几步且要可解释 → ReAct。
3. **步骤多、顺序重要吗？** 是 → Plan-and-Execute。
4. **多个调用互不相干、要快？** 是 → ReWOO（并行）。

### 5. 把术语接到你做过的事上（面试杀手锏）

这是把"答不上"变成"答得比别人好"的关键话术：

> "我两个项目正好用了**两种范式**：飞书 PM Agent 是**标准 ReAct**（Harness 原生 loop，最多 4 步）；FitGenius 是**单次结构化输出 + 受控指令集**，不是 ReAct——因为移动端要低延迟、而且我把爆炸半径锁死在 3 个指令内，**不需要循环**。
> 用 ReAct 的时候我也踩过它的坑：串行慢、容易陷入死循环，所以我加了**步数上限（4 步）**和**工具白名单**来治它。"

这段话值钱在三点：① 证明你知道 ReAct 之外的选择；② 证明你知道 ReAct 的**缺点**并且真的治过；③ 说明你是**按场景选范式**，不是只会一种。

### 6. 万一被追问"在美团业务里怎么用"

- **商家经营助手**：商家问"今天单量为啥掉了" → ReAct：Thought（要看订单/流量/竞对）→ Action（调经营看板）+ Action（调竞对数据）→ Observation → 给结论和建议。
- **智播实时交互**：观众问"这个套餐含不含饮料" → ReAct 调商品库 → 回答（第四节气 3 写过商家 Agent）。
- 多工具可并行的场景（同时查天气 + 库存 + 竞价）→ 提一嘴 ReWOO 能并行提速，显你懂优化。
