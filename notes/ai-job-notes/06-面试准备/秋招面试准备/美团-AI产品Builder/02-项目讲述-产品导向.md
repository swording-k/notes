## A. FitGenius — 独立 0→1 AI 健身产品【最对"个人 AI 产品"优先项】
- **痛点**：健身新手"不会练、练不准、难坚持"——计划到执行有断层。
- **产品闭环**：个性化计划 → 训练执行 → 动作反馈 → 恢复判断 → 下次调整。
- **AI 怎么用**：多模态模型生成计划 + 饮食分析；Apple Vision 本地动作识别评分。
- **落地**：调研 → 需求拆解 → 交互设计 → 开发 → App Store 上架（现 1.5.1），种子用户 30+，按反馈迭代动作分析 / Watch / 身体报告。

## 深度补答：收益 / 边界 / 困难（二面必问，逐项目答）

> 二面（+2 领导面）最爱戳的三类深度题：**"带来了什么收益 / 功能价值？" / "边界在哪、什么场景不该用？" / "具体遇到什么困难、怎么解决？"**
> 下面每个项目都按这三问给**可直接口述的答案**，全部产品语言，守住红线（不编数字、不泄内部信息）。前面 A / B 是重点，二面最可能被深挖。

### A. FitGenius（重点，二面最可能被深挖）

**① 收益 / 功能价值**
- 核心功能价值：把"专业健身教练"从"贵、不随时在"变成"手机里随时可用的个性化教练"，降低了普通人获得专业训练指导的门槛。
- 验证（不编数字）：种子用户 30+ 真实使用并反馈，产品按反馈迭代出"动作分析 / Watch 模块 / 身体报告"三个方向 —— 说明**需求是被真实验证过的，不是自嗨**。
- 完整走通 0→1：从调研、需求拆解、交互设计到 App Store 上架（现 1.5.1），证明我能独立把 AI 产品从想法推到用户手里。
- 一句口语版（二面准备）：*"这个产品的功能价值是'让健身新手随时有个个性化教练'；验证方式不是看模型多强，而是 30+ 种子用户的真实反馈驱动了后续三个方向的迭代。"*

**② 边界 / 模型能力边界（二面高频"什么场景不该用大模型"）**
- 动作识别边界：Apple Vision 本地识别关键点，但复杂动作 / 遮挡场景下识别不准 → 所以 AI **不能替代真人教练做细到关节角度的动作纠错**，产品定位是"辅助"不是"替代"。
- 大模型边界：计划生成依赖大模型，但大模型"不懂你身体的实时状态" →所以我又新增了“身体报告”这个板块，去获取 iPhone 或 Apple Watch 上一些详细的睡眠以及心率等数据，让智能体更理解用户的健康状况，个性化程度和准确度更高。而且 设计上让 AI 做"建议"而非"决定"，用户始终掌控，避免"AI 替你做主"。
- 适用人群边界：面向健身新手和规律训练者，不是给专业运动员做竞技训练方案。
- **为什么讲边界是加分项**：这恰恰对应 JD 里"判断一个 AI 功能是否真正解决问题 / 设计可信 AI 交互" —— 你展示的是"我知道 AI 该用在哪、不该用在哪"，而不是"什么都要上模型"。

**③ 遇到的困难 + 怎么解决**
- 困难1（最大阻碍，已详答）：用户觉得 AI"一改就乱动整个计划"、失控 → 决策上放弃"每次重生成完整计划"的简便，选"AI 只做增减量修改"，把交互改成指令式（用户说"今天太累减重量"→ 系统只动那一块）。
- 困难2：大模型偶发输出不稳定（非合法结构）→ 产品侧决策不是"修 parser"，而是**让任何 AI 异常都落在可控的几次固定操作里，用户永不看到 raw error** —— 这是"保证体验不崩"的产品决策，不是技术修补。
- 困难3：个人开发者资源有限 → 先做"计划 + 反馈"闭环而非铺功能，用种子用户反馈定优先级（先补动作分析，再补 Watch / 报告）。

**④ 准确性怎么判断 / 怎么保证不崩（二面极高概率深挖，必准备）**

> 面试官问法："你是怎么测试 / 判断 AI 回答准确性的？怎么保证它不崩？"
> 你担心的点：**确实没跑过几万条自动化测试** —— 这完全 OK，关键是把"没跑大数据集"讲成**有意识的产品决策**，而不是"我没做测试"。

**先讲"不崩"（这块你有真工程，直接讲，最稳）：**
- **结构化输出 + 鲁棒解析**：system prompt 强制模型只返回 JSON；再用一个**括号匹配解析器**（`extractJSONObject`）从模型可能夹带的废话 / ```json 围栏 / 转义引号里抽出合法 JSON 对象，支持嵌套大括号 —— 模型哪怕"话痨"也解析得出来。抽不到再退回清理后的纯文本。
- **类型安全解码**：抽出的 JSON 用 `JSONDecoder().decode(PlanJSON.self)` 强类型解码，字段不对直接走失败分支，不会把脏数据塞进 UI。
- **优雅降级，绝不裸崩**：
  - 初次生成计划：解析失败 → 落到**本地安全兜底计划**（硬编码的健康模板），用户永远看到一份可用计划，不会白屏/报错。
  - **重新生成计划（关键决策）**：解析失败 → **主动抛错并保留旧计划**，而不是静默落一个"不相关的兜底计划"。原因：早期版本静默兜底会让用户以为"已按我的要求改好"，实际却是固定增肌模板 —— 表现就是"乱改 / 没按我改"。我**刻意改成报错+保留旧计划**，把"假成功"变成"明确的失败提示"，用户体验反而更诚实可控。
  - 对话改计划：解析不出指令 → 直接当普通文本回复，不显示 JSON 给用户。
- **受限动作空间（兜底中的兜底）**：AI 改计划只能发出 **3 种固定指令**（`update_plan` / `add_exercise` / `remove_exercise`），且动作名必须从注入的"动作库"里选、回连 `ExerciseTemplate`。即便模型" reasoning 错了"，它**物理上无法执行任何超出这 3 类的离谱操作** —— 把"答错"的爆炸半径锁死在极小范围。

**再讲"准确性怎么判断"（诚实 + 产品视角，这是加分项）：**
- **先坦诚边界**：我没有、也不该在 0→1 阶段跑几万条标注测试集 —— 因为健身计划没有唯一标准答案（"这份计划好不好"是高度个人化、场景化的），用固定测试集衡量生成质量本身就是错的。
- **我的真实做法，分三层**：
  1. **把"答错"的代价锁小**：靠上面那套"结构化输出 + 受限指令 + 动作库回连"，模型只能在"合法计划 JSON / 3 种指令"里产出，错误形态有限、可预期，不需要靠海量测试去兜底未知崩溃。
  2. **用户进回路 = 终极校验**：生成计划后 App 展示给用户**确认 / 调整**才生效；重新生成时把"当前计划"注入上下文让 AI 基于真实计划改、不另起炉灶，且把用户原话标为"最高优先级必须严格执行"。**真正的 ground truth 是用户本人，不是测试集**。
  3. **定性反馈闭环**：30+ 种子用户的真实使用反馈驱动了"动作分析 / Watch 模块 / 身体报告"三个迭代方向 —— 这是比准确率数字更真实的质量信号（用户是否真的跟着练、是否觉得准）。
- **一句口语版（二面直接背）**：*"准确性的判断我没走几万条标注测试集 —— 因为健身计划没有唯一标准答案，那种测法本身不对。我的做法是：先用结构化输出 + 受限指令把'答错'的爆炸半径锁死，再用'用户进回路确认 + 种子用户定性反馈'当终极校验。不崩靠工程兜底，准不准靠人验，而不是靠我单方面宣称模型多强。"*

### B. 长城证券 · 飞书项目管理智能体（重点）

**① 收益 / 功能价值**
- 落地验证：MVP 已被 2 个团队实际使用，支撑日常需求 / 任务管理 —— 真实可防御。
- 功能价值：把"人盯项目、需求散落、状态靠人工"变成"智能体在群里随时写入 / 查询需求任务"，让协作状态可见、降低追踪成本。
- 产品价值：验证了"需求 ≠ 任务"建模能跑通真实协作 —— 这是你区别于纯开发的核心差异化。

**② 边界 / 模型能力边界**
- 模型边界：LLM 可能"幻觉"写出不符合领域模型的字段 → 所以设计**白名单 harness（模型零裸权限，只能走业务工具）**，且输出必须符合状态机 —— 这是"AI 不能裸奔"的产品决策。
- 场景边界：适用于"结构化协作"（需求 / 任务 / 状态），**不适用于开放创意讨论** —— 知道智能体该用在哪。
- 数据边界：内部系统，不对外（红线，对外一律泛化"某券商"）。

**③ 遇到的困难 + 怎么解决**
- 困难1（最大阻碍）：智能体容易"乱来"、不可信 → 决策：先定义领域模型与权限边界，**再**接 LLM，放弃"快速出 demo"换"可控可信"；迭代五版 PRD 收敛。
- 困难2：让非技术同事愿意用 → 设计成"在群里 @ 一下就能用"，降低使用门槛（产品体验决策）。
- 困难3：多需求多任务追溯混乱 → 用 RTM 需求追踪矩阵（需求 ↔ 任务双向映射）解决。
