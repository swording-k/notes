## 一、核心项目：飞书项目管理智能体（"项目管理大王"）

### 1.1 一句话技术定位（开场用）
> "我做了一个**不依赖飞书 Aily 的本机常驻飞书机器人**：飞书事件经 WebSocket 长连接到达本机，Python 服务负责触发策略、去重和调度，官方 **DeepSeek Harness** 负责模型规划和受限工具编排，Python bridge 用飞书 API 读写已授权的多维表格。它能在群里识别项目意图、安全写入需求/任务、主动巡检并推送日报周报。"

### 1.2 架构分层（文字版，面试画图可用）

```
┌─ 飞书开放平台（自建应用）─────────────┐
│  身份 / 事件推送(im.message.receive_v1) / API 权限      │
└──────────────────┬────────────────────┘
                   │ WebSocket 长连接（事件到达 Mac/服务器）
┌─ Python 常驻服务（feishu-pm-agent）────┐
│  长连接接收 · 触发策略(21触发词) · 30min去重       │
│  调度器(工作日16:35巡检/周五14:43周报) · 飞书API · 持久化 │
└──────────────────┬────────────────────┘
                   │ 自然语言 + 上下文
┌─ DeepSeek Harness（官方，dsh CLI）──────┐
│  模型规划 + 受限工具编排（Shell/文件/网页/子agent 全禁用） │
└──────────────────┬────────────────────┘
                   │ JSON Lines 白名单工具请求（只暴露项目管理操作）
┌─ Python Bridge（harness_bridge.py）────┐
│  ALLOWED_TOOLS 白名单校验 → ProjectTools → 飞书 Bitable 写入 │
└────────────────────────────────────────┘
```

### 1.3 和你昨天学的 Agent 循环——**完全对上（重点！）**

`src/feishu_pm_agent/agent.py` 里的 `Agent.handle()` 就是昨天我给你写的伪代码的**真实版**：

| 昨天的理论 | 你代码里的真实实现 |
|---|---|
| 「大模型决定用哪些工具」 | `response = self.llm.complete(messages, project_tool_schemas())` |
| 「通过 harness 执行一轮」 | `result = self.tools.execute(response.tool_name, ...)` |
| 「把结果喂回对话，循环」 | `messages.append(assistant_message)` + `messages.append(tool_result)` |
| 「多轮循环，不是一轮」 | `for iteration in range(self.max_iterations)`（**max_iterations=4**） |
| 「大模型判断达成目的就结束」 | `if response.final_text is not None: return response.final_text` |
| 「超过轮数不写」 | 循环结束返回"操作步骤过多，未写入数据" |

**面试话术**："我这个 Agent 就是标准的 ReAct 工具循环——LLM 决策调哪个工具、bridge 执行、结果回灌对话，最多 4 步，超过就拒绝写入，避免模型瞎写。"

### 1.4 harness 层（呼应昨天的 harness 学习——你的破学历筹码）

- 用**官方 DeepSeek Harness** 当编排层（`harness_gateway.py` 用 `subprocess` 调 `pnpm dsh --profile headless --patch ...`），模型只负责规划。
- **安全隔离 = 昨天讲的"沙箱/约束执行"真实落地**：Harness 默认的 Shell、文件、网页、子 agent 工具在项目管理 profile 里**全部禁用**，只留项目管理白名单；模型**没有直接调飞书 API、没有 Shell/文件系统权限**——想写数据只能走 `harness_bridge.py` 的 `ALLOWED_TOOLS` 白名单。
- bridge 用 **JSON Lines** 协议（`handle_json`）只暴露 16 个白名单操作（create_requirement / assign_task / update_task_status / read_feishu_document …），非法操作直接拒。

**面试话术**："我研究过 DeepSeek Harness 的插件机制和约束执行——落地时我把模型权限收到最小：它不能直接碰飞书 API 或 Shell，只能走我白名单里的项目管理工具。这跟 Codex Harness 的硬沙箱思路一致，都是'让模型能干活但出不了格'。"

### 1.5 飞书接入（证明你懂"接各个接口/后端"）

- **事件接入**：`im.message.receive_v1` 走 WebSocket 长连接（不是 Webhook），本机常驻接收。
- **鉴权**：`messenger.py` 里 `_get_tenant_access_token()` 用 app_id/app_secret 换 tenant_access_token（带缓存），Bearer 鉴权调发消息/拉历史接口。
- **数据层**：`bitable.py` 是**飞书多维表格 REST 适配器**（记录超 100 条自动翻页，不漏历史）；写入回执带真实 `record_id` + Base 链接。
- **意图层**：`intent.py` ——群内不 @ 但命中 **21 个触发词**（要做/派给/工时/里程碑/Sprint…）才响应，普通聊天静默；`dedup.py`/`event_dedup.py` 做 30 分钟业务去重 + message_id 去重防飞书重复投递。

### 1.6 生产级工程点（证明你不止"玩具"，懂真实后端）

这些是真实后端该有的东西，面试主动提能拉开差距：
- **可观测性**：日志只记事件类型 / 脱敏 chat / 工具名 / 成功失败 / 耗时，**绝不记 API key、App Secret、令牌、文档正文**。
- **错误处理**：飞书/模型/Harness/Base 失败**绝不虚构成功**；写失败不二次猜测写入。
- **调度韧性**：工作日 16:35 巡检、周五 14:43 周报；单次调度异常不终止长连接；Mac 睡眠/断网不可用时迁移到 Linux 服务器用 `systemd` 常驻。
- **真实 battle scar（最值钱）**：`agent.py` 注释写明——"DeepSeek 推理模型要求把 `reasoning_content` 回显，否则多步工具调用会报 **HTTP 400**"。这是你真调通过 DeepSeek 推理模型留下的坑，面试官一听就知道你真干过。

### 1.7 面试 1–2 分钟逐字稿（背熟）
> "我做过一个飞书项目管理智能体，是本机常驻机器人，不依赖飞书 Aily。飞书群消息通过 WebSocket 长连接到本机 Python 服务，我先做意图识别和去重，再把自然语言交给 DeepSeek Harness 做规划和受限工具编排。模型不能直接碰飞书 API，只能走我白名单里的项目管理工具去读写多维表格——最多 4 步工具循环，超了就拒绝写入，保证安全。它还工作日自动巡检、周五自动出周报。整个链路我踩过 DeepSeek 推理模型必须回显 reasoning_content 否则 400 的坑，也做了脱敏日志和不虚构失败的错误处理。"

### 1.8 可能被深挖的问题 + 预案
- **Q：为什么不用飞书 Aily，要自己接 Harness？** A：Aily 是平台托管，灵活度和工具白名单可控性不如自己用 DeepSeek Harness 编排；我要的是"模型零裸权限、只走白名单"的硬约束。
- **Q：模型怎么不直接调飞书 API？** A：最小权限原则 + 防注入/防误写；所有写操作经 bridge 白名单校验，且写入回执带 record_id 可追溯。
- **Q：4 步上限怎么定的？** A：项目管理动作一般 1–3 步完成，4 步是安全上限，超了说明意图不清，宁可拒绝让用户拆分，也不胡写。
- **Q：并发/性能？** A：单机常驻、事件驱动，当前量级够；生产迁 Linux + systemd 常驻，调度独立捕获异常不影响长连接。

### 1.9 飞书 Aily 平台技术路线 vs 你的自研（面试高频深挖，先纠正一个误解）

> ⚠️ **先纠正**：你猜"Aily 是靠飞书给自己的 traecli 对飞书做了适配才效果好"——**这个理解不对，得改**，否则被懂行面试官一听就露。

**① "traecli" 不是 Aily 的底层**
- Trae 是字节跳动的 AI IDE（类似 Cursor），和飞书 Aily 不是同一个产品、不是 Aily 的底层。
- 飞书自己的编程智能体叫**飞书妙搭**（类 Claude Code 的 Code Agent）；飞书生态里的 Agent 执行框架叫 **OpenClaw**（开源）。你很可能把"妙搭 / OpenClaw"和"Trae"搞混了。

**② Aily 真实技术栈（2026 公开资料）**
- **飞书原生集成（最根因）**：Aily 是飞书内置智能伙伴，消息 / 文档 / 多维表格 / 日历 / 任务 / 妙记全是飞书自己的数据，它**直接调内部接口**，不需要"适配"外部系统。
- **MCP 协议 + OpenClaw**：用 MCP 连企业已有系统（不改造源系统即可接入），用 OpenClaw 做本地 Agent 执行调度。
- **Multi-Agent 协同**：需求澄清 / 规划 / 检索 / 报告等"领域专家" Agent 分工。
- **专属运行环境**：可跑 Python、处理 Office/PDF、生成多种格式文件。
- **模型无关路由**：通义 / DeepSeek / Kimi 等按任务路由。

**③ 为什么 Aily "效果好"——是平台优势，不是适配技巧**
Aily 不需要像你的自研项目那样"接飞书开放 API"，因为它**本身就是飞书**。你的项目是**外部应用**，必须走 `im.message.receive_v1` 事件 + `tenant_access_token` 鉴权 + Bitable REST 适配器——你写的这套 Python 后端，正是"外部应用硬接飞书"的代价，也是你**真懂 Python 后端接接口**的证据。Aily 作为亲儿子，零迁移成本、数据随手可得，效果自然好。

**④ 面试怎么讲这个差异（话术）**
> "飞书 Aily 是平台原生方案，数据都在飞书内部、零接入成本；我这个项目是外部自建应用，必须用飞书开放平台的 WebSocket 事件、tenant_access_token 鉴权和 Bitable REST 去接——这套'接各个接口的后端'恰恰是我工程能力的体现。两者路径不同，但都验证了我对 Agent + 企业系统集成的理解。"
