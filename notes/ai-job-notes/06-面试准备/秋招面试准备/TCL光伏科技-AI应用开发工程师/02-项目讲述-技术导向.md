## 一、长城证券·项目管理智能体（主线，最匹配 JD）

> 详细技术版见 `09`（长城证券内部用飞书 Aily 落地；自研飞书版在 09）。这里给面试讲述骨架。

**业务背景**（30 秒）：长城证券金融科技研发中心实习，发现内部项目协同"需求散落、任务追踪靠人、状态不可见"，做了一套智能体系统。

- **需求拆解**：拆成 3 个核心实体——项目 / 需求 / 任务，多对多关系 + **RTM（需求跟踪矩阵）**双向追溯；每个实体有状态机（草稿/进行中/评审/完成/阻塞）。
- **技术选型**：底层飞书 Aily（金融合规、低代码）；模型服务走 LLM API + Function Calling；领域模型与飞书多维表格打通。
- **核心实现**：FSM 状态流转（事件驱动）、短期记忆（session）+ 长期记忆（Aily 知识库）、5–6 个工具（查项目/建任务/改状态/报表/通知）、多轮对话拆解参数。
- **迭代与落地**：五版 PRD（v1 可行性 → v2 权限审计 → v3 对话流 → v4 报表 → v5 性能）；单团队 → 两个团队。
- **讲述用时**：5–7 分钟，重点讲**状态机、工具调用、记忆机制**（正好命中 JD 第 2 条）。

## 二、FitGenius（Apple Vision 本地动作识别 —— 端侧 AI 代表作）

### 2.1 一句话技术定位
原生 iOS 健身 App（SwiftUI / SwiftData，已上架 1.5.0，种子用户 30+）。技术上最特别的是：**用 Apple Vision 框架在手机本地做姿态估计给用户动作评分**，云端 LLM 只负责生成训练计划/饮食建议。

### 2.2 Apple Vision 动作识别原理（重点，讲细）
很多人以为"AI 动作识别"是云端大模型，其实 FitGenius 是**端侧推理**，原理分四步：

1. **取帧**：摄像头实时采集视频帧（不是整段上传，是逐帧处理）。
2. **姿态估计（Pose Estimation）**：调用 Apple 原生 **Vision 框架的 `VNDetectHumanBodyPoseRequest`**，检测出人体 **19 个关键点**（左右肩、肘、腕、髋、膝、踝 + 鼻/颈等），连成"人体骨骼"。
3. **关节角度比对**：根据关键点算出各关节角度（比如深蹲时膝夹角、髋夹角），和**标准动作模板（`ExerciseTemplate`）**里的"标准角度区间"比对，偏差越大说明动作越不标准。
4. **评分策略引擎**（这是工程亮点，不是简单比对就完）：
   - `pose-frame-quality-policy`（帧质量策略）：先过滤掉**模糊 / 人物被遮挡 / 没拍全**的低质量帧，只评好帧，避免误判。
   - `pose-feedback-planner`（反馈规划）：根据角度偏差生成**纠正建议**——"膝盖内扣""下蹲不够深""背部前倾过多"。
   - `workout-completion-policy`（完成策略）：判定一个动作算"完成一次"、计数、是否达标。

**为什么端侧**：模型跑在 iPhone 本地（Core ML），不把视频传云 → **隐私好、延迟低、不依赖网络**。这正是"端云协同"的典型：重活（姿态评分）本地干，轻活（生成计划）云端干。

### 2.3 端云协同架构
- **本地**：Vision 姿态估计 + 评分策略引擎（实时、隐私）。
- **云端**：AI 计划/饮食通过**腾讯云 CloudBase 云函数**（`fitgenius-api`）代理 MiniMax-M3 生成（iOS 包内不含任何 API key；也支持 App 内"直连模式"填自有 Key 完全不依赖后端）。
- **Apple Watch**：`WatchWorkoutManager` 采运动传感器（心率等），和 iPhone 联动。

### 2.4 面试怎么讲（1–2 分钟）
> "我独立做了一个上架的 iOS 健身 App。技术上最有趣的是动作识别：用 Apple Vision 的姿态估计检测人体 19 个关键点，和标准动作模板比关节角度，再用一套'帧质量 + 反馈规划 + 完成策略'的引擎评分，全程在手机本地跑、不传云。云端 LLM 只负责生成计划。这让我真正理解了端侧 AI 和云端 LLM 的分工——这也是现在很多 Agent 在做的'端侧感知 + 云端决策'。"

### 2.5 训练计划生成：你问的「AI 操作 App」到底是什么（重点，讲细）

你说"通过提示词让大模型返回 JSON 格式的训练计划，渲染到 app 页面，看起来像 AI 在操作系统而不是返回文字"——**完全正确，而且这就是这个项目最值得讲的技术点。** 它属于 LLM 应用架构里的一支：**结构化输出（Structured Output）+ 指令式交互**。代码证据（`AIService.swift`）非常明确：

**① 首次生成整份计划（`generateInitialPlan`）**
- 用 `initialPlanSystemPrompt`（系统提示）+ 用户画像（user 消息）调 LLM，**在提示里强制要求"只返回 JSON"**。
- LLM 流式返回文本后，用 `extractJSONObject(from:)` 从文本里抠出那个 JSON 对象（模型常会带回车/废话/` ```json ` 围栏，所以要自己解析）。
- 用 `JSONDecoder().decode(PlanJSON.self)` 把 JSON 变成 Swift 的 `WorkoutPlan` 数据模型 → SwiftUI 自动渲染成"第几天练什么"的页面。
- 解析失败 → `fallbackPlan()` 给一份**本地写死的兜底计划**（不调模型）。

**② 对话里改计划（`chat`）—— 这就是"AI 操作 App"的核心**
- 系统提示写明：**"如果用户想改训练计划，必须返回 JSON 格式"**，并给了 `actionJSONExample` 模板。
- 模型返回后，先试 `parseActionCommand` 解析成 `AIActionCommand`：
  - `type` 只有三种：`update_plan` / `add_exercise` / `remove_exercise`
  - 每个 action 带 `day`、`old_exercise`、`new_exercise`、`exercise_name`、`sets`、`reps`、`weight`、`reason`
- **关键一行**：`if let command = try? parseActionCommand(...)` 成功时，函数返回 `("", command)` —— **故意返回空字符串 + 指令**。意思是：屏幕上**不显示任何 AI 文字**，App 上层直接拿这条 command 去改 `WorkoutPlan` 数据，SwiftUI 一重渲染，用户就"看到计划被改了，但没看到 AI 说话"。**这就是你感觉"AI 在操作 App"的来源**——技术本质是把模型输出当成"操作指令"而非"聊天回复"。

**③ 工程亮点（面试加分，都是真踩过的坑）**
- `extractJSONObject` 自己写了一个**括号匹配解析器**（处理转义引号、嵌套 `{}`），而不是直接 `JSONDecoder`——因为 MiniMax 等模型常返回"根据原则…```json{…}```"这种带前缀/围栏的脏输出，硬 decode 会失败 → 改不了计划。
- `regeneratePlan` 解析失败时**故意抛错**而不是偷偷给兜底（代码注释写得很直白："会让用户误以为已按我的要求改好，实际却是固定模板，表现就是乱改/没按我改"）——这是个很成熟的工程判断。
- `matchTemplate`：AI 返回的动作名会**回连到本地动作库 `ExerciseTemplate`**，这样能顺带接通 GIF 演示和动作详情页——让模型在约束内生成、又能接回本地富媒体。

### 2.6 校准：这算「Agent」吗？（避免面试被追问露馅）

你直觉里说"做了一些 agent 的思想"——方向对，但要**精确措辞**，否则被深问会露：

- **准确说法**：这是 **「单次 LLM 调用 + 结构化输出（Structured Output）」**，是 Agent 范式的一个**子集 / 基础设施**，不是完整 Agent。
- **完整 Agent**（像你飞书智能体项目）是：模型**自己决定**调哪个工具 → 执行 → 结果喂回 → 循环多轮（`for` 循环、`max_iterations`）。模型是"决策层"。
- **FitGenius 这里**：模型是**被 prompt 约束输出固定 JSON schema**，App 拿到 JSON 当指令执行。模型**不自主决定调工具、不循环**。
- **两者关系**：结构化输出是 Agent 能跑起来的底座之一——Agent 的工具定义、工具返回结果，本质也是约定好的结构化格式。所以你"用 prompt 让模型返回 JSON 再渲染"和"Agent"是**近亲**，但严格说 FitGenius 这处是"**单次 LLM + 结构化输出**"，不是多轮工具调用 Agent。
- **面试话术**：讲"我做过两种：一种是结构化输出式的 LLM 应用（FitGenius 用 JSON 指令操作 App 数据），另一种是完整的多轮 Agent（飞书项目用 DeepSeek Harness 做工具循环）——两者底层都是'让模型输出机器可读的结构'。" 这句话既诚实又把两块经验串起来了。

## 三、开源贡献：Atoll（灵动岛指令中心）& Workisland（AI Agent 智能监控）

### 3.1 Atoll —— macOS「灵动岛」到底是什么技术原理

**先澄清一个概念**：MacBook 有"刘海（notch）"但没有 iPhone 那种硬件灵动岛。Atoll（SwiftUI 原生 macOS 应用，GPL v3，下载 7.5 万 +、3.9k Stars）是**用软件仿真了一个灵动岛**。

- **灵动岛 UI 原理**：Atoll 在刘海区域用 SwiftUI 画一个**胶囊状 UI**，默认收缩成一条，鼠标 hover 或手势（双指下滑）触发 **SwiftUI spring 展开动画**，切换不同面板（媒体 / 系统状态 / 计时器 / 剪贴板 / 终端等）。
- **核心状态机**：`DynamicIslandViewCoordinator`（一个 `ObservableObject`）管所有状态，用 `SneakContentType` 枚举区分音乐 / 音量 / 电池 / 计时器等；`toggleSneakPeek` 做**短暂预览**（比如调音量时闪一下），`toggleExpandingView` 做**持续展开**；用 Swift Concurrency 的 `Task` 管自动隐藏计时器。
- **媒体控制原理**（你简历里的"媒体控制"）：基于 macOS **Now Playing / MediaRemote 框架**，读取当前播放器（Apple Music / Spotify / Cider）的状态，控制播放/暂停/切歌、显示内联封面预览。这是 Atoll 从开源项目 **Boring.Notch** 继承的核心能力。
- **系统监控原理**：CPU/GPU/内存/网络/磁盘用量通过 **SMC（System Management Controller，系统管理控制器）** 读取（架构源自开源 Stats 项目），在灵动岛显示。
- **日历/提醒原理（你问的"也是 macOS 开放接口吗"）**：**是的，正是 macOS 开放的官方框架 `EventKit`**（`import EventKit` → `EKEventStore`）。Atoll 通过它读取系统日历和提醒事项，需要用户在"系统设置 → 隐私与安全性 → 日历"里授权（Info.plist 里的 `NSCalendarsFullAccessUsageDescription` 就是这个 TCC 授权弹窗文案）。代码里 `CalendarService` 用 `predicateForEvents` 按时间范围查事件，`CalendarManager` 还监听 `.EKEventStoreChanged` 通知做实时刷新。除此之外，它还支持**第三方日历 App（Notion Calendar / Fantastical）**通过 URL Scheme 打开对应事件——这是另一种"开放接口"（URL scheme），但**读取日程本身用的是 EventKit**。
  - ⚠️ 一句话记：Atoll 的日历 = EventKit（苹果官方开放框架）+ TCC 授权；和媒体控制（MediaRemote）、系统监控（SMC）一样，都是**调 macOS 给第三方 App 开放的官方 API**，不是自己黑进去的。

**我的贡献**：
- Issue #539 主导设计 **AI coding agent 管理中心**——为多种 AI 编程 Agent 设计统一展示/调度层（状态机管 Agent 运行/等待/完成/错误，消息队列管通知）。
- PR #566 日历优化、PR #544 中文性能面板修复。

### 3.2 Workisland —— AI Agent「智能监控」是什么技术原理

**关键认知**：Workisland（Node.js 22 + TypeScript 本地优先 macOS 应用，Apache 2.0）**自己不实现 Agent，而是"监控别人的 Agent"**——这恰恰是你理解 agent 框架的最佳切入点。

- **它解决什么**：多个 coding agent（Claude Code / Codex / Cursor…）在后台跑，贵的不是启动它们，而是**注意到"哪个在等你做决定"、再找回对应终端**。Workisland 把这套状态收拢到 Mac 灵动岛附近。
- **监控原理：两种本地信号互补**（核心创新）：
  1. **Hooks（钩子）**：Claude Code / Codex 等 agent 在 PreToolUse / PostToolUse / 停下等用户输入时，会触发你配置的 hook 脚本，把事件（running / approval needed / question waiting / completed / failed）发给 Workisland。
  2. **Transcript watching（监听转录文件）**：实时监听 agent 的 transcript 文件变化、解析状态——当一种信号不可用时，另一种仍能观测到任务完成。
- **适配器（Adapter）模式**：为 Claude Code / Codex / Cursor / Trae / **WorkBuddy** / **DeepSeek Harness** 等每种 agent 写 first-party adapter，统一成 Workisland 内部任务模型（所以你能看到这些 agent 的真实事件格式）。

**我的贡献**：产品初创成员 / collaborator——设计**通知策略**（什么该弹、什么静默、优先级排序）、搭建 **macOS 签名/公证流水线（GitHub Actions）**（CI/CD 工程能力）、内测 20+。

### 3.2.1 三个技术澄清（面试防追问）

**① Workisland 的"灵动岛"和 Atoll 是同一套技术吗？—— 不是，只是视觉概念相同。**
- Atoll：SwiftUI **原生** macOS 应用，在刘海区用原生视图**真·仿真灵动岛**（画布 + spring 动画）。
- Workisland：**Electron（Node.js + TypeScript）+ React** 的跨平台壳（`node_modules/electron`、`release/.../Electron Framework.framework` 可证），它的"island"是 `src/renderer/island/` 里用 **JSX/DOM/CSS 画的一个"灵动岛样式"悬浮面板**（IslandPanel.js、MediaCard.js 等），不是原生 macOS API。
- 而且严格说：**苹果从没给第三方开放过"灵动岛"API**（灵动岛是 iPhone 14 Pro 硬件特性；Mac 刘海屏的"灵动岛"是 Atoll 这类 App 自己用 SwiftUI 仿真出来的）。所以 Workisland 在 Mac 上**不可能**调原生灵动岛 API，它只能是前端模拟一个"island 视觉"。
- 一句话：两者只是都做了"顶部中央胶囊聚合信息"的**产品形态**，技术栈完全不同（原生 SwiftUI vs Electron+React）。
- **校准一个常见误解（"为了更容易做 Windows 端"）**：Electron 确实是跨平台框架，但 **Workisland 当前只发了 macOS 版**——`package.json` 的 `build` 配置只有 `mac`（dmg / arm64），`package:mac` 脚本只打 Mac 包，描述写的是"macOS 本地"，**没有 `win` / `linux` 配置**。而且**就算以后做 Windows 版，也做不出"灵动岛"**——Windows 没有刘海屏、没有灵动岛这个概念，只会复用"Agent 监控中心"的底层逻辑、把 UI 换成 Windows 形态（系统托盘 / 悬浮窗）。Atoll 锁死 macOS 则是**物理必然**：SwiftUI 是苹果专有框架、且灵动岛依赖 Mac 刘海屏，根本无法移植到 Windows。

**② 各家 agent 的 Hooks 原本为什么留出接口？（你问"总不是为了让用户做这种智能体监听吧"）**
- 你的直觉对——**hooks 被发明绝不是"为了让用户监听 agent"**。它的设计动机是软件工程的**开放-封闭原则 / 插件化**：agent 框架（Claude Code / Codex / DeepSeek Harness / Cursor）是**通用工具**，框架方不可能预知每个团队要什么额外逻辑，于是把"agent 执行的生命周期节点"暴露成可编程扩展点，让个性化需求交给用户侧。
- 框架方原本指望 hooks 干这些正经事：
  1. **安全与合规**：PreToolUse 拦截危险命令（`rm -rf`）、限制文件访问范围、防密钥泄露；
  2. **质量保障**：PostToolUse 自动 lint / 格式化 / 跑测试 / 类型检查；
  3. **流程自动化**：Stop 钩子自动提交、生成 summary、发通知；
  4. **可观测性/审计**：记录 agent 干了什么（这是"监控"的合法子集，但只是用途之一）。
- **"智能体监听"（像 Workisland 用 Hooks + transcript 监控状态）是 hooks 落地后的一个创造性应用，不是它被发明的原因。** 但因为 hooks 把"agent 在跑/在等/完成/失败"这些事件暴露出来了，Workisland 顺势把它当信号源——这恰恰说明你**深度理解了 agent 框架的扩展机制**（这也是面试该讲的亮点）。

### 3.3 这两个项目对面试的价值
- 它们正好覆盖你简历里的"AI Agent"关键词：Atoll 做了 Agent 管理中心的**状态机**，Workisland 深度接触了 Claude Code / Codex / DeepSeek Harness 等 agent 的 **hook / transcript 机制**——**你对主流 agent 框架不是纸上谈兵**。
- 而且它们是 **Swift / TS 原生应用**，证明你不止会 Python，能写跨平台原生 AI 工具（这点对"AI 应用工程师"岗是加分项）。

## 四、技术导向讲述的 5 个原则

1. **用"我设计了 X 架构"代替"我负责了 X 业务"**——产品岗的"负责/推动"在这面试官眼里含金量低。
2. **多讲技术选型的"为什么"**——为什么选 Aily 不自建？为什么动作识别端侧跑不传云？每个选型背后要有 trade-off。
3. **讲工程痛点和解决方案**——比如 LLM API 限流、Token 太长怎么压缩、Agent 工具调用失败怎么重试、低质量帧怎么过滤。
4. **量化效果用工程指标**——"准确率 / 响应 < 2s / 内测 20+ 人"比"用户说好"有力。
5. **诚实承认短板**——"这块我没做过但我会学"比硬撑好。JD 是初级岗，学习自驱力占不小权重。

## 五、可能被深挖的问题（提前演练）

- **FitGenius**："Apple Vision 姿态估计怎么做的？""为什么端侧不传云？""动作评分的误差怎么控制？"（答：帧质量策略过滤坏帧 + 标准模板角度区间比对）
