## 一、先分清：ReAct 不是 React.js

| | **ReAct** | **React.js** |
|---|---|---|
| 中文常读 | 「瑞艾克特」Agent 推理范式 | 「瑞艾克特」前端框架 |
| 本质 | 大模型 **Reasoning（推理）+ Acting（行动）** 的交互范式 | 前端 UI 组件框架 |
| 作用 | 让模型一边想、一边调用工具、一边观察结果，循环直到完成任务 | 构建用户界面，组件化 + 虚拟 DOM |
| 场景 | Agent 做决策、查数据、执行操作 | 网页 / App 前端开发 |
| 关系 | **和 React.js 完全没有关系**，只是英文名像 | — |

**面试中先澄清**：如果面试官问「React 框架和智能体框架有什么优缺点」，大概率他指的是 **ReAct（Reasoning + Acting）这个 Agent 推理范式**，而不是前端 React.js。你可以说：「我先确认一下，您说的是 Agent 里的 ReAct 范式，还是前端 React.js 框架？这两个名字很像。如果是 Agent 的 ReAct，我的理解是……」

## 二、ReAct 是什么、优缺点

### 一句话
**ReAct = 让模型「边想边做」**：每步先生成一段 Reasoning（解释为什么要这么做），再生成一个 Action（调用工具 / 执行动作），拿到 Observation（观察结果）后再进入下一步，循环直到停止条件触发。

### 流程
```
用户提问
  ↓
Reasoning：我需要先查一下数据库里的客户信息
  ↓
Action：query_customer_db(name="张三")
  ↓
Observation：{"name":"张三","order_id":"12345"}
  ↓
Reasoning：现在我知道订单号了，可以查物流
  ↓
Action：query_logistics(order_id="12345")
  ↓
Observation：{"status":"已签收"}
  ↓
Answer：您的订单已签收
```

### 三个优点
1. **可解释性强**：每步都有 Reasoning，能看到模型「为什么做这个动作」
2. **能纠正错误**：Observation 是真实外部反馈，模型发现错了可以调整下一步
3. ** grounding 好**：不是纯脑补，而是靠工具/环境拿到真实信息

### 四个缺点（你问的死循环在这里）
1. **容易死循环 / 无限循环**：如果 Action 设计不好、停止条件不明确，模型可能在原地打转（比如反复查同一个接口）
2. **串行慢**：一步做完才能做下一步，无法并行调用多个工具
3. **上下文膨胀**：每轮 Reasoning + Action + Observation 都塞进上下文，轮数多了会爆窗口、成本飙升
4. **对模型能力要求高**：既要会推理，又要会选工具、又要会从 Observation 中总结——弱模型容易跑偏
5. **缺全局规划**：走一步看一步，复杂任务可能前期走错后面全错

**对应你的项目经验**：飞书 PM Agent 里设了 **4 步上限** 和 **工具白名单**，就是为了防 ReAct 的死循环和上下文膨胀——这是你可以直接举的实证。

## 三、CoT 是什么、和 ReAct 的关系

### CoT = Chain-of-Thought（思维链）
让模型在给出最终答案之前，先生成一段中间推理过程。典型 prompt：「Let's think step by step.」

**例子**：
> 问：一个停车场有 5 辆车，每辆车 4 个轮子，还有 2 辆摩托车，每辆 2 个轮子，一共有多少个轮子？
> CoT 回答：车有 5×4=20 个轮子，摩托车有 2×2=4 个轮子，总共 20+4=24 个轮子。

### CoT 的优点
- 提升数学、逻辑、常识推理能力
- 可解释性比直接给答案好

### CoT 的缺点
- **没有外部反馈**：只能在自己脑子里想，不能查数据库、不能调用 API、不能执行动作
- **无法处理实时信息**：知识截止到训练数据，不能获取最新信息
- **模型可能一本正经胡说**：推理过程也是生成的，可能看起来合理但结果错了

### ReAct vs CoT 一句话区分
- **CoT：只想不做**（纯推理，不调用工具）
- **ReAct：边想边做**（推理 + 工具调用 + 观察反馈）

**关系**：ReAct 可以看成 **CoT 的扩展版**——在 CoT 的推理链中间插入了 Action 和 Observation。CoT 是 ReAct 的子能力。

### 再补两个常见范式
| 范式 | 特点 |
|---|---|
| **Plan-and-Solve** | 先整体规划步骤，再执行。解决 ReAct「缺全局规划」的问题，但规划本身也可能错 |
| **Tree-of-Thoughts (ToT)** | 多路径探索 + 回溯，像下棋一样。适合解谜、数学，但成本高 |
| **Multi-Agent** | 多个 Agent 分工协作。不是单 Agent 自己循环，而是不同角色对话 |

## 四、这些不是「做 WorkBuddy / 豆包」的框架，而是框架内部的推理方式

**ReAct / CoT 不是应用框架，而是 Agent 的推理范式（思考方式）**。就像「递归」不是编程语言，而是一种算法思想。

真正的 Agent 平台 / 框架是这些：

| 平台/框架 | 定位 | 和 ReAct/CoT 的关系 |
|---|---|---|
| **WorkBuddy** | AI 编程助手 / Agent 平台 | 内部可能用 ReAct 或类似范式驱动 Agent Loop |
| **豆包 / Coze** | 字节 AI Bot / Agent 搭建平台 | 工作流 / 插件调用可能基于 ReAct/CoT 思想 |
| **LangChain / LangGraph** | Agent 开发框架 | 提供 ReAct Agent 的实现封装 |
| **AutoGen** | 多 Agent 对话框架 | 用对话实现 Multi-Agent，底层仍可嵌 ReAct |
| **CrewAI** | 多 Agent 角色协作框架 | 角色分工 + 任务流程 |

**面试中可以这样回答**：「ReAct、CoT 是大模型做决策时的推理范式，不是 WorkBuddy 或豆包这种具体产品。WorkBuddy 作为一个 AI 编程助手平台，它内部执行用户任务时很可能用了类似 ReAct 的循环：理解需求→调用 MCP 工具→观察结果→再行动。我的 PM Agent 项目里也是这个思路：模型 + Harness + 工具白名单 + 步数上限，本质就是 ReAct 的工程化落地。」

## 六、把这些概念和你的项目挂上钩（面试主动讲）

### 1. PM Agent → ReAct / 工具白名单 / 步数上限
> 我做的 PM Agent 本质上就是 ReAct 的工程化落地：模型接到需求后，会调用需求拆解、任务拆分、RTM 追踪等工具，观察结果后再决定下一步。为了防止死循环和上下文膨胀，我做了两件事：一是 **ALLOWED_TOOLS 白名单**，模型只能调我授权的 14 个 PM 工具；二是 **4 步上限**，超过就停下来让人工确认。这两个约束正好对应了 ReAct 的两个主要缺点。

### 2. FitGenius → 什么场景不用 ReAct
> FitGenius 里用户改健身计划是一个输入相对确定、输出必须是结构化 JSON 的场景。我们没有用 ReAct 循环，而是直接用 system prompt + schema 约束 + 温度 0 做一次性结构化输出。因为任务太简单，上 ReAct 只会增加延迟和成本，得不偿失。这说明 **ReAct 不是银弹，要看场景选范式**。

### 3. AI Coding 工作流 → 你怎么用这些范式提效
> 我日常用 Claude Code / Codex 写代码时，会观察它的行为：先计划（类似 Plan-and-Solve）→ 分步改文件 → 运行测试 → 看报错再修复（类似 ReAct 的 Observation 反馈）。所以我理解这些范式的最好方式就是每天在用它们，也知道它们的边界。

## 八、Codex / Claude Code / DeepSeek Harness 的设计方式对照（你的真实疑问）

### 先给结论
**这三个工具底层是同一个范式——ReAct（模型 + 工具层 + 循环）——但工程实现各有侧重。** 面试官问这个问题，是想看你有没有真正理解这些工具，而不是背定义。

### DeepSeek Harness（你读过源码，确认一下理解）
**你的直觉完全正确：它底层就是 ReAct 思想——模型思考 → 调用工具 → 返回结果 → 检查是否达到目标 → 再 loop 循环。** 我刚读了它的源码确认：

- **架构**：由 Cordis 框架驱动，**「一切皆插件」**——模型适配器、工具注册表、会话日志、**连 Agent Loop 本身（`core/agent-loop`）都是一个插件**，全部可以从配置（cordis.yml）里替换
- **循环引擎**：`agent-spine` / `core/agent-loop` 就是 ReAct 驱动：模型 reasoning → 调工具（bash / str-replace-editor，走 guarded execution 防护管道）→ 观察结果 → 判断是否达目标 → 循环
- **脚手架**：沙箱策略（landlock 隔离）、工具护栏、会话持久化（JSONL append-only 日志）、批准策略、system prompt 拼装
- **所以 dsh = ReAct Loop + 可插拔/可替换的工程脚手架**

### 三个工具对照表

| 工具 | 范式内核 | 设计侧重 | 和其他两个的区别 |
|---|---|---|---|
| **Claude Code** | ReAct | 交互式、权限门控、子 Agent 并行 | 每个危险操作要人工确认；可派子 Agent 并行探索；有 plan mode 先做整体规划 |
| **OpenAI Codex** | ReAct | 沙箱隔离 + 测试验证驱动 | 在**隔离沙箱**跑，用**测试/类型检查/Lint 作为 Observation 信号**——写完就跑测试，看失败再修（把 ReAct 的「观察」强化成「自动验证」） |
| **DeepSeek Harness** | ReAct（core/agent-loop） | 插件化、可替换、工程脚手架 | 模型/工具/loop 全是插件，从配置替换；重沙箱隔离 + 工具护栏 + 会话持久化；是「框架」不是「成品 App」 |

### 面试标准答法（背这个）
> 它们底层都是同一个范式——**ReAct：模型 + 工具层 + 循环**。但工程实现各有侧重：
> - **Claude Code** 是交互式 ReAct，强调权限门控（危险操作人工确认）和子 Agent 并行；
> - **Codex** 是沙箱化 ReAct，特别把「测试 / 类型检查」当成观察信号，写完代码就跑测试、看失败再修；
> - **DeepSeek Harness** 我读过它的源码，它是一个插件化 Harness（Cordis 框架驱动，**连 Agent Loop 本身都是可替换的插件**），loop 依然遵循 ReAct 思想，但额外提供了沙箱隔离、工具护栏、会话持久化这些脚手架。
>
> 所以我的理解是：**ReAct 是共同内核，差异在于如何约束和优化这个 loop**。我自己的 PM Agent 其实也用了同一套思路——模型 + Harness + 工具白名单（对应 dsh 的 guarded execution）+ 4 步上限（对应 bounded loop），本质就是 ReAct 的工程化落地。

### 你之前「没读太清楚」的点，补一句
dsh 和你读到的那种「一个 while 循环调 LLM」的最大不同，是它把**一切拆成插件**——这让它能被 fork 后定制（这正是你评估它当公司 Agent 平台底座的原因）。所以面试官若追问「和 Claude Code 比有什么不一样」，你就答：**Claude Code 是成品 App，dsh 是给开发者 fork 定制的框架，loop 可被替换、模型可被替换、工具可被替换**。
