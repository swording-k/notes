## 1. FitGenius 健身智能体 App（独立 0→1 iOS）

**技术面可能问：**
- Q1：整体技术架构是怎样的？
- Q2：Apple Vision 动作识别具体怎么做的？
- Q3：为什么动作评分放端侧、不传云？
- Q4：训练计划怎么保证大模型返回的是"可被 App 用的结构"？
- Q5：你说的"AI 操作 App"是怎么实现的？
- Q6：LLM 输出经常带脏字符 / 围栏，你怎么解析？
- Q7：这算 Agent 吗？和你的飞书智能体有什么区别？

**回答要点：**
- **架构（端云协同）**：本地用 Apple Vision 做姿态估计 + 评分（Core ML 端侧推理）；云端 LLM 通过腾讯云 CloudBase 云函数（`fitgenius-api`）代理 MiniMax-M3 生成计划/饮食；Apple Watch 的 `WatchWorkoutManager` 采运动传感器与 iPhone 联动。iOS 包内不含任何 API key，也支持"直连模式"填自有 key。
- **动作识别（四步）**：摄像头逐帧 → `VNDetectHumanBodyPoseRequest` 检 19 个关键点 → 按关键点算关节角度，与标准动作模板 `ExerciseTemplate` 的角度区间比对 → 评分策略引擎（帧质量策略过滤模糊/遮挡帧 + 反馈规划生成纠正建议 + 完成策略判定计数）。
- **为什么端侧**：隐私好（不传视频）、延迟低、不依赖网络——典型"端侧感知 + 云端决策"分工。
- **结构化输出**：`initialPlanSystemPrompt` 在提示里强制"只返回 JSON"；流式返回后 `extractJSONObject` 抠出 JSON → `JSONDecoder().decode(PlanJSON.self)` 变成数据模型 → SwiftUI 渲染；失败走 `fallbackPlan()` 兜底。
- **"AI 操作 App"本质**：chat 模式系统提示要求改计划必须返回 JSON；`parseActionCommand` 解析成 `AIActionCommand`（type 仅三种：`update_plan` / `add_exercise` / `remove_exercise`），成功后函数返回 `("", command)`——**故意空文字 + 指令**，App 拿 command 直接改数据模型重渲染，用户"看到计划被改但没看到 AI 说话"。
- **脏输出处理**：自写括号匹配解析器（处理转义引号、嵌套 `{}`、```json 围栏），不硬 `JSONDecoder`；`regeneratePlan` 解析失败**故意抛错**而非偷偷兜底（避免"看起来改了实际没改"的骗感）——这是成熟工程判断。
- **是否 Agent**：准确说 FitGenius 这是**单次 LLM + 结构化输出**，是 Agent 范式的子集/基础设施；完整 Agent 是多轮"模型决策调工具→执行→回灌→循环"（飞书项目才是）。话术：两种都做过，底层都是"让模型输出机器可读的结构"。

## 2. 长城证券 · 飞书项目管理智能体

**技术面可能问：**
- Q1：整体架构怎么设计的？
- Q2：为什么选飞书 Aily 不自建一套？
- Q3：领域模型（项目/需求/任务）怎么设计？
- Q4：状态机怎么实现？
- Q5：工具调用出错怎么处理？Token 成本怎么控？
- Q6：五版 PRD 迭代，技术上每版解决了什么？

**回答要点：**
- **架构**：飞书 Aily（金融合规、低代码、原生集成）作底座 + LLM API + Function Calling；领域模型与飞书多维表格打通；5–6 个工具（查项目/建任务/改状态/报表/通知）；短期记忆（session）+ 长期记忆（Aily 知识库）。
- **为什么 Aily**：金融场景合规优先、不重复造轮子、飞书生态内权限/审计现成；自研成本高且踩合规坑。
- **领域模型**：核心抽象是"需求 ≠ 任务"——多对多（M:N）关系 + RTM（需求跟踪矩阵）双向追溯；每个实体有状态机（草稿/进行中/评审/完成/阻塞）。这是产品建模也是工程建模。
- **状态机**：事件驱动流转，FSM 管状态变更；工具调用走白名单，越权拒绝，失败回灌模型重试。
- **成本/稳定性**：上下文压缩/摘要控 Token；工具执行失败分级处理（可重试 vs 需人工）。
- **迭代**：v1 可行性 → v2 权限审计 → v3 对话流 → v4 报表 → v5 性能；从单团队扩到两个团队实际使用。

## 4. Atoll 开源（collaborator）

**技术面可能问：**
- Q1：灵动岛是硬件还是软件仿真？
- Q2：媒体控制怎么拿到 Spotify 状态的？
- Q3：系统监控 / 日历分别用什么读的？
- Q4：核心状态机怎么设计的？
- Q5：你主导的 AI coding agent 管理中心怎么落地？

**回答要点：**
- **仿真本质**：MacBook 有刘海无硬件灵动岛，Atoll 用 SwiftUI 在刘海区画胶囊 UI，hover/手势触发 spring 展开——**软件仿真**，非苹果官方 API。
- **媒体控制**：基于 macOS Now Playing / MediaRemote 框架读当前播放器（Apple Music / Spotify / Cider）状态并控制。
- **系统监控**：CPU/GPU/内存/网络/磁盘通过 SMC（System Management Controller）读。
- **日历**：macOS 官方 `EventKit`（`EKEventStore`）+ TCC 授权；`CalendarService` 用 `predicateForEvents` 查事件，监听 `.EKEventStoreChanged` 实时刷新；第三方日历通过 URL Scheme 打开。
- **状态机**：`DynamicIslandViewCoordinator`（`ObservableObject`）管状态，`SneakContentType` 枚举区分类型，`toggleSneakPeek`（短暂预览）/ `toggleExpandingView`（持续展开），Swift Concurrency `Task` 管自动隐藏。
- **我的贡献**：Issue #539 主导设计 AI coding agent 管理中心（状态机管 Agent 运行/等待/完成/错误 + 消息队列管通知）；PR #566 日历优化、PR #544 中文性能面板修复。
- 验证数据：下载 7.5 万+、3.9k Stars（公开可查）。

## 5. Workisland 开源（collaborator / 产品初创成员）

**技术面可能问：**
- Q1：你怎么监控一个 agent 的状态？
- Q2：为什么用 Electron + React？灵动岛和 Atoll 同技术吗？
- Q3：Hooks 原本设计动机是什么？
- Q4：你搭的 CI/CD 流水线做了什么？

**回答要点：**
- **监控双信号**：① Hooks（Claude Code / Codex 等在 PreToolUse / PostToolUse / Stop 触发脚本发事件：running / approval needed / question waiting / completed / failed）；② Transcript watching（实时监听 agent 转录文件解析状态）。一种不可用时另一种仍可见——鲁棒性设计。
- **适配器模式**：为 Claude Code / Codex / Cursor / Trae / WorkBuddy / DeepSeek Harness 各写 first-party adapter，统一成内部任务模型。
- **技术栈**：Electron（Node.js + TypeScript）+ React 跨平台壳；"island"是 JSX/DOM/CSS 画的悬浮面板，**非原生 API**。当前只发 macOS 版（package.json build 仅 mac）。
- **Hooks 动机**：开放-封闭/插件化——框架方把生命周期节点暴露成扩展点，正经用途是安全拦截（rm -rf）、质量保障（lint/测试）、流程自动化、可观测性。"智能体监听"是创造性应用，非发明原因——这恰恰说明你深度理解 agent 框架扩展机制。
- **我的贡献**：设计通知策略（什么弹/什么静默/优先级）；搭 macOS 签名/公证流水线（GitHub Actions）；内测 20+。
